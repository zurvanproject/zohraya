## ممیزی ورودی

جست‌وجوی کل درخت main و شاخهٔ #81 برای نام ماژول، شناسهٔ schema، importها و
فراخوان‌های verify/append انجام شد.

| مسیر | رفتار موجود | نتیجه |
|---|---|---|
| CLI: `history --verify PATH` | متن فایل → `strict_loads` → `verify` | کلید تکراری پیش از ساخت دیکشنری رد می‌شود |
| `verify_json(text)` | `strict_loads` → `verify` | ورودی عمومی مناسب برای متن/بایت JSON |
| `verify(dict)` | بررسی ساختار، هش، ریشه و بازپخش | برای دادهٔ درون‌حافظه؛ تکرارِ حذف‌شده قابل بازیابی نیست |
| `append(dict, ...)` | ابتدا `verify`، سپس کنترل head و تولید کپی | API درون‌حافظه؛ مجوز بدن تولید نمی‌کند |
| `demo()` و آزمون‌ها | دادهٔ ساخته‌شده در همان فرایند | json.loads این مسیر، ورودی بیرونی دریافت نمی‌کند |

در کد ممیزی‌شده endpoint، job یا importer دیگری برای schema تاریخچه یافت نشد.
خواننده‌های تجربهٔ طراحی، checkpoint صفات و fixture فیزیک schemaهای دیگری دارند؛
آنها مسیر ورود این تاریخچه نیستند و در این تغییر بازنویسی نشده‌اند.
هیچ ادعایی دربارهٔ فراخوان‌های خارج از مخزن یا شاخه‌های آزمایشی بررسی‌نشده نداریم.
فراخوان آینده باید متن اصلی را به `verify_json` یا CLI بدهد؛
`verify(json.loads(external_text))` مرز مناسبی برای ورودی بیرونی نیست.

## تغییر افزوده و آزمون‌ها

منطق `history.py` و `strict_json.py` و هر ۱۶ آزمون #66/#81 عیناً حفظ شد.
کمبود واقعی اتصال CI برطرف شد: تغییر runtime بدن یا تابع manifest منبع آن
اکنون آزمون ژنوم را فعال می‌کند. CI همچنین ساخت/بازپخش تاریخچه در CLI و
ثابت‌ماندن فایل‌های runtime را بررسی می‌کند.

پنج آزمون تکمیلی این موارد را پوشش می‌دهند:

- تطابق دقیق هش قالب تولیدشده با کد تاریخی #66؛ schema و نسخه تغییر نکردند.
- رد نسخهٔ ناشناخته در تاریخچه، ریشه، checkpoint و genotype حتی پس از محاسبهٔ مجدد هش.
- رد کلید تکراری تودرتو/escapeشده و تغییر bool/number از طریق CLI، بدون نوشتن فایل ورودی.
- رد تغییر منبع بدن به جای بازپایه‌گذاری خاموش تاریخچه.
- ثابت‌ماندن checkpoint یک بدن مصنوعی و تمام فایل‌های runtime در موفقیت و شکست تاریخچه.

## مرز مجوز و انتشار

این انتقال فقط کد پیشنهاد/اعتبارسنجی است؛ نه اعمال پیشنهاد روی بدن.
فایل‌های `runtimes/tadash_body`، وضعیت زنده، ژنوم مالک، حافظه و تنظیم API تغییر
نمی‌کنند. قرارداد فعلی به منبع قدیمی موجود در main متصل می‌ماند؛ این انتقال
مهاجرت به بدن مرجع جدید یا تأیید هیچ تغییر اندامی نیست.

هش زنجیره اصالت نویسنده یا مجوز کاربر را اثبات نمی‌کند. حذف یک پسوند معتبر یا
بازنویسی سازگار کل زنجیره همچنان به head مورد اعتماد بیرونی برای تشخیص نیاز دارد.
کنترل head درون‌حافظه نیز قفل چندنویسندهٔ فایل نیست.

مرحلهٔ ۱ در PR #83 ارائه شد. مرحلهٔ ۲ فقط پس از موفقیت CI و بررسی SHA دقیق،
پس از مرحلهٔ ۱ ادغام می‌شود. PRهای #20/#66/#81 به‌عنوان سوابق شاخه‌های اصلی
باز می‌مانند تا وابستگی‌های دیگر آنها بدون بازنویسی تاریخچه حفظ شود.
