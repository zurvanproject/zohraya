# مقایسهٔ حافظهٔ Hermes و جست‌وجوی آفلاین ناسورایا

۲۷ اکتبر ۲۰۲۶. این آزمایش به درخواست سهند و با دادهٔ ساختگی اجرا شد. Hermes نسخهٔ `v0.22.5`، commit دقیق `bf0203a794a07aac3ff764972ab9087baa4e4f4e`، از مخزن [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent/tree/bf0203a794a07aac3ff764972ab9087baa4e4f4e) دریافت شد. از کد اصلی فقط `SessionDB` روی پایگاه موقت اجرا شد؛ هیچ مدل، API، gateway یا زمان‌بند فعال نشد.

## آنچه بررسی و اجرا شد

Hermes نشست و پیام را در SQLite با WAL نگه می‌دارد، به پیام شناسه می‌دهد و با FTS5 جست‌وجو می‌کند. سازوکار بازیابی گفتگو ادامهٔ خودکار اثراتی مانند اجرای ابزار یا حرکت بدن را تضمین نمی‌کند. سازندهٔ پایگاه Hermes می‌تواند ساختار پایگاه و نمایه را مدیریت یا تغییر دهد؛ به همین علت نباید با آن به دفتر واقعی ناسورایا اشاره کرد.

با SessionDB واقعی سه پیام فارسی مصنوعی ذخیره شد، پردازش پایان یافت و پردازش تازه همان رکورد `تعادل` را یافت. در همین نمونه، جست‌وجوی `تعادل AND چرخش` هیچ پیام مشترکی نداشت اما Hermes دو پیام مجزا را نیز برگرداند؛ رفتار کاهش محدودیت جست‌وجوست و نباید به‌عنوان یافتن هر دو واژه در یک پیام برداشت شود. `ناسورايا` با «ي» عربی نیز `ناسورایا` با «ی» فارسی را نیافت. اینها مشاهده‌های همین نسخه و مجموعه‌دادهٔ آزمایشی هستند، نه ادعای جامع دربارهٔ همهٔ حالت‌های Hermes. جزئیات در `integration/hermes-memory-search-v01/hermes-probe.json` است.

در بررسی کد واردکردن خارجی Hermes، تطبیق تکراری بر شناسهٔ خارجی یا مسیر تکیه دارد؛ این تطبیق به‌تنهایی تضمین نمی‌کند محتوای فایل تغییر نکرده است. نمایش export با پیام‌های فشرده نیز لزوماً نسخهٔ قابل‌بازیابی همهٔ وضعیت‌های فعال/غیرفعال نیست. بنابراین این کار هیچ پایگاه Hermes یا آرشیو قدیمی را وارد حافظهٔ فعال نکرده است.

## جست‌وجوی جداگانه روی آرشیو ناسورایا

یک جست‌وجوی مستقل الهام‌گرفته از FTS5 به `nasuraya.history_search` اضافه شد. این کد Hermes را کپی یا پایگاه آن را باز نمی‌کند. ابتدا `history.load_history` از PR #88، آرشیو و چکیدهٔ مستقل آن را بررسی می‌کند؛ سپس فقط متن پیام‌های ثبت‌شده در نمایهٔ SQLite موقت داخل حافظه قرار می‌گیرد. نمایه برای هر درخواست از نو ساخته می‌شود. برنامه شناسهٔ آرشیودار، شناسهٔ محلی، متن اصلی، `conversation://`، برچسب ارزیابی تألیفی و وضعیت نتیجه را برمی‌گرداند.

در نمایه برای تطبیق بهتر، نویسه‌های ی و ک فارسی/عربی، ارقام و اعراب نرمال می‌شوند؛ متن برگشتی عین متن اصلی است. جست‌وجوی چندواژه‌ای فقط پیام‌هایی را برمی‌گرداند که همهٔ واژه‌ها را داشته باشند؛ افت خودکار به OR وجود ندارد. علامت‌ها عملگر SQL/FTS محسوب نمی‌شوند. محدودیت ورودی ۲۵۶ نویسه، هشت واژه و حداکثر ۳۲ نتیجه است؛ یک آرشیو پل گفتگوی فعلی حداکثر ۳۲ پیام دارد. جست‌وجو صرفاً روی پیام است، نه رسید یا یادگیری عددی؛ جست‌وجوی زیربخشی یا معنایی پیاده نشده است.

```bash
python -m nasuraya.history_search \
  --archive /path/to/history.json --expected-sha256 YOUR_PINNED_SHA256 \
  --query 'تعادل بدن'
python -m nasuraya.history_search_tests
```

فراخواننده ابتدا با ابزار PR #88 آرشیو خواندنی را صریح می‌سازد و SHA آن را جداگانه نگه می‌دارد. پایگاه‌های مبدأ، حافظهٔ فعال، پیش‌بینی، بودجه و وضعیت بدن دست‌نخورده می‌مانند؛ متن تاریخی اجازهٔ اجرای حرکت نیست. پیامِ وضعیت نامعلوم با همان برچسب بازگردانده می‌شود. آرشیو ناسازگار یا SHA غلط رد می‌شود. این جست‌وجو روی متن کاربر به معنی صحت مستقل محتوا نیست.

## اعتبارسنجی و محدودیت

۱۰ آزمون متمرکز جست‌وجو موفق شد؛ شامل فارسی، عربی، جست‌وجوی چندواژه‌ای، جلوگیری از عملگر تزریقی، هش غلط، فرایند تازه، حفظ byte فایل مبدأ و جلوگیری از فراخوانی بدن و affect. اجرای واقعی Hermes نیز روی دادهٔ موقت در دو فرایند مجزا انجام شد؛ فقط وابستگی `ruamel.yaml` در محیط موقت نصب شد.

این یک اتصال دائمی، مهاجرت حافظه، یکپارچه‌سازی خودکار، اجرای مدل محلی یا گوش‌دادن خودکار به ChatGPT نیست. از وجود فایل آرشیو واقعی یا سازگاری داده‌های واقعی کاربر نتیجه‌ای گرفته نشده است. اجرای probe اختیاری، نیازمند checkout همان commit و Python دارای ruamel.yaml است:

```bash
python integration/hermes-memory-search-v01/probe_hermes.py --hermes-root /path/to/hermes-agent --python /path/to/isolated-python
```

## بازبینی استمرار: چند آرشیو و آزادسازی اتصال موقت

در بازبینی بعدی یک ایراد بازتولید شد: `with sqlite3.connect(...)` تراکنش را مدیریت می‌کند اما اتصال را صریح نمی‌بندد. در API تکرارشونده، اتصال‌ها ممکن بود تا جمع‌آوری خودکار حافظه باز بمانند. دو آزمون موفقیت و خطای SQL این ایراد را پیش از اصلاح نشان دادند؛ اکنون `contextlib.closing` هر دو مسیر را می‌بندد. خروج پردازش CLI قبلاً اثر را محدود می‌کرد؛ این اصلاح قابلیت استفادهٔ تکراری در یک پردازش را بهتر می‌کند.

برای ادامهٔ کار میان نشست‌ها، API جدید `search_collection` می‌تواند هم‌زمان یک تا چهار آرشیو صریح را جست‌وجو کند. CLI با تکرار جفت‌های مسیر و pin، وقتی بیش از یک جفت دارد همین مسیر را فراخوانی می‌کند:

```bash
python -m nasuraya.history_search \
  --archive /path/to/first.json --expected-sha256 "$FIRST_PIN" \
  --archive /path/to/second.json --expected-sha256 "$SECOND_PIN" \
  --query 'تعادل بدن'
```

مسیرها و pinها به ترتیب فهرستشان جفت می‌شوند؛ تعدادشان باید برابر باشد. هر pin باید از export پیشین، مستقل از فایل فعلی، نگه داشته شده باشد. برنامه هیچ pinی را از فایل ورودی استنتاج یا تولید نمی‌کند. تمام آرشیوها قبل از جست‌وجو بررسی می‌شوند؛ یک فایل خراب، pin غلط یا منبع ناسازگار کل درخواست را رد می‌کند و نتیجهٔ ناقص برنمی‌گرداند. حجم واقعی bytes خوانده‌شده در مجموع حداکثر ۶۴ MiB است؛ هر آرشیو حداکثر ۳۲ پیام دارد و سقف خروجی ۳۲ پیام است. کپی خصوصیِ همان bytes برای اعتبارسنجی استفاده می‌شود؛ مبدأ تغییر نمی‌کند.

هر نتیجهٔ چندآرشیوی، علاوه بر متن و شناسهٔ اصلی، `archive_sha256` و `source_binding_id` دارد. ID محلی یکسان در دو نشست یکی فرض نمی‌شود. دو export هم‌پوشانِ یک نشست نیز جدا می‌مانند و تجربه‌های مستقل محسوب نمی‌شوند؛ انتخاب خودکار «نسخهٔ تازه‌تر»، حذف تکرار معنایی یا ادغام حافظه انجام نمی‌شود. pin تکراری رد می‌شود. ترتیب داخلی بر اساس SHA آرشیو و شناسهٔ تاریخی مرتب می‌شود تا عوض‌کردن ترتیب ورودی، رتبه‌بندی یا نتیجه را تغییر ندهد. همهٔ واژه‌های پرسش باید در همان یک پیام باشند.

API و شکل خروجی تک‌آرشیوی `/1` دست‌نخورده مانده‌اند؛ خروجی مجموعه، schema جداگانهٔ `nasuraya.history-fts-collection/1` دارد. متن همچنان گفتهٔ تاریخی فراخواننده است؛ وضعیتِ نتیجهٔ نامعلوم یا منشأ تألیفی ارتقا داده نمی‌شود. این قابلیت به مدل گفت‌وگوی فعلی حافظهٔ زنده یا استمرار خودکار اضافه نمی‌کند؛ افزوده‌ای به کد پروژه است.

شواهد بازبینی و خروجی آزمون‌های تک‌آرشیوی، مجموعه‌ای و آزادسازی منابع در `integration/history-search-continuity-v02/` نگه داشته می‌شود. فایل‌های اتصال فعال گفتگو، تجربه و منابع بومی بدن تغییر نکرده‌اند.
