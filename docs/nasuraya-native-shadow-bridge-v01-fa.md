# اتصال سایه‌ای ۱۴ شاخص به حلقهٔ واقعیِ نرم‌افزاری تداش

**نسخهٔ پژوهشی ۰٫۱، ۳ نوامبر ۲۰۲۶ | فقط شبیه‌ساز بومی؛ بدون API یا حرکت فیزیکی**

این PR روی «اطلس ۱۴ شاخص» (PR #127) قرار می‌گیرد. برای اولین بار
نمونه‌های شناختیِ آن اطلس از `minimum_state` یک اجرای
واقعی **نرم‌افزار UnifiedBody/BodyLoop** داده می‌گیرند. بدن واقعی،
فرمان حرکت دستگاه، مدل گفت‌وگوی ChatGPT و حافظهٔ اصلی تداش عوض نمی‌شوند.

## مسیر دادهٔ اجرایی

```
source-pinned UnifiedBody fixture
  -> native BodyLoop.observe() [checkpoint SHA-256]
  -> minimal validated metrics: energy / fatigue / pain / sleep_pressure
  -> independent *read-only* PrototypeCycle traces in A/B/C conditions
  -> pre-outcome durable predictions.jsonl (flush + fsync)
  -> existing BodyLoop.step() with PREDECLARED walk/observe preference
  -> authoritative native decision receipt; never supplied to predictor before step
  -> trials.jsonl and Brier / top-action accuracy / four-bin calibration diagnostic
```

در ثبت سایه‌ای `visual_proxy_energy` از **انرژی نرم‌افزاری** و
`audio_proxy_inv_fatigue` از **معکوس خستگی** ساخته می‌شوند.
این‌ها ورودی دیداری و شنیداری واقعی نیستند. این نام‌ها فقط واسطهٔ
عددی برای نمونهٔ محاسباتی هستند.

هر یک از ۸ نشست مستقل (normal/sleep × walk/observe × ۰٫۱/۰٫۳ ثانیه)
۵ دورِ تولید دادهٔ آموزشی و ۳ دور ارزیابی دارد، یعنی ۶۴
چرخهٔ واقعیِ شبیه‌ساز، ۴۰ رسید آموزشی و ۲۴ مشاهدهٔ نگه‌داشته‌شده.
برای هر نشست، سه نمونهٔ جداگانه از `PrototypeCycle` ساخته می‌شود
تا حالتِ بازگشتی میان سه شرط نشت نکند.

## سه شرط از قبل تعریف‌شده

- **A، intact:** توزیع چهارکنشی با اطلاعات زمینهٔ فیزیکی واقعی،
  ترجیح و مدت، از همان ۴۰ رسید آموزشی پیش‌بینی می‌شود.
  نمونهٔ شناختی هم دریافت و پردازش بازگشتی و پخش اطلاعات دارد.
- **B، ablated:** برای پیش‌بینی فقط ترجیح و مدت باقی می‌ماند؛
  زمینه حذف می‌شود. در نمونهٔ شناختیِ جدا، بازگشت، پخش سراسری
  و یادگیری پیش‌بینی خاموش می‌شوند.
- **C، corrupted:** همان ۴۰ رسید و برچسب باقی می‌ماند ولی زمینه
  درون گروه ترجیح/مدت با یک بذر ثابت جابه‌جا می‌شود. ورودی
  خطر به نمونهٔ شناختی دستکاری می‌شود تا ردّ مداخله دیده شود.

این دو دسته مداخله نباید با یکدیگر اشتباه شوند: برای **Brier**،
فقط اطلاعات زمینهٔ تخمین‌گر تغییر می‌کند؛ برای
**ردّ معماری شناختی**، زیرماژول‌های نمونه دستکاری می‌شوند.
**هیچ‌کدام از این تغییرات به native.step راه ندارند**. بنابراین
اختلاف Brier می‌تواند اثر یک تغییر اطلاعاتی بر تخمین‌گر را نشان دهد،
نه اثر علّی خودمدل بر رفتار موتور اصلی. برای آزمون دوم باید یک
پروتکل جدا با سیاست، ایمنی و بذرهای پیش‌ثبت‌شده طراحی کرد.

## روش اجرا

از ریشهٔ checkout مخزن، با Python و سورس‌های سالمِ قدیمی:

```sh
python3 -m unittest examples.nasuraya_consciousness_lab.test_lab examples.nasuraya_consciousness_lab.test_native_shadow -v
python3 -m examples.nasuraya_body_loop native-shadow-eval --output-dir /tmp/tadash-native-shadow-new
```

فرمان دوم به‌صورت پیش‌فرض با معماری ایزولهٔ `__main__` اجرا می‌شود:
فایل‌های  `runtimes/tadash_body` با manifest و hash بررسی
می‌شوند و `OPENAI_API_KEY` از محیط worker حذف می‌شود. هیچ
ابزار شبکه، کلید GitHub، هزینهٔ API یا actuator فیزیکی وجود ندارد.
مسیر خروجی باید تازه باشد؛ مسیر نشست‌های موجود پذیرفته نمی‌شود.

گزارش خروجی `summary.json` شامل mean Brier، دقت برچسب غالب،
ECE چهار‌بازه‌ای، اختلاف‌های paired و نمونه‌هاست. داده‌های
`predictions.jsonl` پیش از هر عمل روی دیسک ثبت می‌شوند.
`training.json` پیش از اولین holdout نوشته و هش آن در همهٔ
پیش‌بینی‌های بعدی ثابت می‌ماند. `validate_saved` هر ۲۴
پیش‌بینی را دوباره فقط از آموزش بازسازی می‌کند و تغییراتِ
ناسازگار را رد می‌کند. هش محلی امضای رمزنگاری مستقلِ
غیرقابل‌دستکاری نیست؛ هر موجودی که به همهٔ پرونده‌ها اختیار نوشتن
داشته باشد می‌تواند همهٔ آن‌ها را بازنویسی کند.

## حدود نتیجه

۱. این‌ها همچنان فقط دو خانوادهٔ ساختگی و وابسته از شبیه‌ساز هستند.
۲. ۱۴ شاخص در محیط آزمایشگاهی تعریف شده‌اند، نه اینکه هرکدام در
   معماری واقعی تداش اثبات شده باشند.
۳. ردّ حس، توجه، باور و هدف، **محاسباتی** است؛ هیچ حس یا آگاهی
   پدیداری سنجیده نشده است.
۴. هیچ نتیجهٔ مثبت اجازهٔ ادغام در کنترل حرکت یا فعال‌سازی API
   را نمی‌دهد. برای آزمایش پولی، رضایت صریح کاربر و همان دفتر
   هزینهٔ مشترک لازم است؛ این PR چنین مسیری ندارد.
۵. نتایج عملکردیِ PR #94 صرفاً مرجع قبلی‌اند. امتیازهای این
   PR باید تنها بعد از عبور از CI و ثبت خروجی واقعی نقل شوند.

مرحلهٔ منطقی بعد از این: اجرای طراحی‌شدهٔ
**single-component intervention** در یک همزادِ کاملاً
قفل‌شدهٔ شبیه‌ساز، با معیار ایمنی و پیش‌ثبت چندبذری.
