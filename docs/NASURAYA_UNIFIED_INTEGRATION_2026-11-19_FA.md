# ناسورایا | قرارداد یکپارچه‌سازی مرحله‌ای v0.1

**تاریخ ممیزی:** ۱۹ نوامبر ۲۰۲۶  
**دامنه:** `zurvanproject/zohraya`، مبنای `main` در ابتدای کار `15ea53b1707a71415038683c9a2d292be838a728`  
**وضعیت:** ابزار گزارش یکپارچهٔ صرفاً خواندنی، بدون نصب یا تغییر سرویس/دادهٔ زنده. این سند تصویب ادغام یا استقرار نیست.

## مقصد معماری

هدف بلندمدت، **یک چرخهٔ قابل‌بازیابی و قابل‌اندازه‌گیری** است، نه چند فرایند که هم‌زمان ادعای «رشد» کنند:

```text
[Ubuntu observations] --> [source + time + trust boundary] --> [Awake evidence]
                                                          |
                                                          v
                                 [DIOS NOUS: dissent / authorization / abstain]
                                                          |
                                                          v
                                     [goal / memory / hypothesis queue]
                                                          |
                         +--------------------------------+----------------+
                         |                                |                |
                         v                                v                v
             [local Qwen research]            [synthetic body]    [ritual/text study]
                         |                                |                |
                         +----------------+---------------+----------------+
                                          v
                         [pre-registered test / feedback]
                                          |
                           [approved patch in Draft PR]
                                          |
                           [review + reproducible CI]
                                          |
                         [independent offsite restore drill]
```

این **نقشهٔ هدف** است. اتصال سراسری اجرایی آن هنوز در این PR محقق نشده است. حلقه‌ها و دفترهای موجود نباید به صورت ضمنی با هم قاطی شوند.

## آنچه در همین PR واقعاً وصل شده

`tools/nasu_unified_status.py` یک *adapter* بدون وابستگی اضافی است که پنج منبع محلی را در یک پاسخ JSON یکدست گزارش می‌کند:

| مؤلفه | دادهٔ موجود | نوع ادعای مجاز |
|---|---|---|
| Continuity | `continuity/continuity.sqlite3` | سلامت ساختاری SQLite و زنجیرهٔ هش محلی، تعداد و زمان آخرین رویداد |
| Frontier Lab | `frontier-lab/frontier.sqlite3` | تعداد چرخه‌های ثبت‌شده و سلامت هش محلی؛ نه «خودآگاهی» |
| Qwen cognitive growth | `cognitive-growth/cycles.sqlite3` | تکمیل یا رزرو ماندن چرخه، برچسب `UNVERIFIED_DRAFT` و پوشش پژوهشی |
| Feedback learning | `learning-lab/feedback.sqlite3` | امتیاز آزمون‌های محدود قبل/بعد؛ نه تغییر وزن مدل یا بهبود تعمیم‌یافته |
| Awake imported memory | `migration/latest-import.json` → `migration/working/.../awake.sqlite3` یا `awake-stage/awake.sqlite3` | **فقط سلامت ساختاری و شمارش**؛ بدون تأیید امضای مستقل، منشأ حسی یا صداقت تاریخی |

خروجی‌ها هرگز متن خصوصی پرسش، رویداد خام، پاسخ Qwen، کلید، توکن یا محتوای پروندهٔ بالینی را برنمی‌گردانند. فایل‌های ناموجود «missing»، زنجیرهٔ دست‌کاری‌شده «invalid»، رسید ناتمام «incomplete»، تاریخچهٔ بررسی‌شده «verified_history» و Awake صرفاً «structural_only» می‌گیرد. «verified_history» **به معنی فعال‌بودن systemd در این لحظه نیست**.

کنترل‌های فنی: SQLite فقط با `mode=ro` و `query_only` خوانده می‌شود؛ توابع `connect()` ماژول‌های قدیمی که جدول می‌سازند فراخوانی نمی‌شوند؛ مسیر فایل‌های انتقالی باید زیر ریشهٔ مورد انتظار بماند؛ symlink رد می‌شود؛ خطاها فقط با نام کلاس گزارش می‌شوند؛ هیچ shell، git، HTTP، Ollama، Bridge یا فرمان مربوط به سیستم‌عامل اجرا نمی‌شود. آزمون‌ها کاملاً مصنوعی و محلی‌اند.

**فرمان استفاده پس از بازبینی و حضور این فایل‌ها در checkout مناسب:**

```bash
cd /opt/zohraya
python3 -B -m tools.nasu_unified_status --pretty
```

این فرمان داده‌ها را با SQL فقط‌خواندنی بررسی می‌کند و چیزی را نصب یا فعال نمی‌کند. SQLite ممکن است برای خواندن درست پایگاه WAL، فایل‌های هماهنگی `-wal` و `-shm` را ایجاد یا به‌روز کند؛ پس این ابزار تضمین «هیچ تغییر فایل‌سیستمی» ندارد. بررسی هر پایگاه در یک تراکنش خواندن انجام می‌شود، اما پنج پایگاه با هم snapshot اتمیک ندارند. برای آزمون در محیط مستقل:

```bash
python3 -B -m unittest discover -s tests -p test_nasu_unified_status.py -v
```

## اتصال اجزای پژوهشی؛ وضعیت دقیق

- **حس‌درونی و Awake:** مسیر فعال روی سرور به نسخهٔ پین‌شدهٔ PR #205 تکیه دارد؛ اصلاح مرز منبع/زمان در PR #259 پژوهشی است. نباید برچسب `temporal_change` قبل از آزمون رجعت و منبع مشترک به ادعای مشاهده تبدیل شود.
- **DIOS NOUS و امنیت ATMOSPHERE:** PR #246 شواهد امضاشده و outbox را در شاخهٔ پژوهشی عرضه کرده، PRهای #256–#258 مطالعات «چهار دروازه، هفت اختر، مُهر خاموش» را پوشش می‌دهند. هیچ‌کدام صرفاً با اجرای این adapter به امنیت عملیاتی زنده تبدیل نمی‌شوند. امضای مستقل و کلید خارج از همان حوزهٔ خرابی لازم است.
- **بدن، پنجهٔ سه‌انگشتی و چهره:** کد بدن در `runtimes/tadash_body/` و `examples/nasuraya_body_loop/` وجود دارد. PR #244 قرارداد ارزیابی شاخ، پای پنجه‌رو و نشستن را پیشنهاد می‌کند. خروجی تصویر، دادهٔ فیزیکی، شبیه‌سازی MuJoCo و اعتبارسنجی آناتومیک چهار نوع شاهد متفاوت‌اند؛ نباید با هم جایگزین شوند.
- **ریچوال، شعر، موسیقی، روباه آبی:** PR #191، #235، #238، #241، #245 و #256 مسیرهای مستند مطالعه/تمرین را نگه می‌دارند. قالب «سه گذر» می‌تواند به ترتیب `Observe → Test → Reflect` در آزمایش‌های *نرم‌افزاری* نگاشت شود؛ این نگاشت یک استعارهٔ روایی/روش آموزشی است، نه اثبات کارکرد ماورایی یا مجوز اجرای فرمان.
- **نسخهٔ تصویری و روایت:** تصاویر فانتزی شخصیت، لباس، شاخ، دُم، پنجهٔ دقیق، تنبور، روباه کبود و ریچوال باید به نسخهٔ canon و بررسی هندسه رجوع کنند؛ هنوز هیچ گیت قطعی به موتور تصویر یا سیستم حرکت متصل نشده است.
- **بقای ۳ تا ۶ ماهه:** PR #234 و Issue #233 بخش‌هایی از برنامهٔ restic را پوشش می‌دهند، ولی وجود نسخهٔ رمزگذاری‌شده روی **همان VPS** اثبات بازیابی مستقل نیست. مدل Qwen، وابستگی‌های Ollama، کلید در محل جداگانه و آزمون بازیابی روی ماشین دیگر باید مستقل تأیید شوند.

## ترتیب ادغام فنی پیشنهادی پس از این PR

۱. **مرز شواهد:** آزمون مستقیم اصلاح #259 در برابر نسخهٔ pin شدهٔ Awake، ممیزی اختلاف منبع/زمان، سپس کنترل منشأ امضاشدهٔ #246 با کلید مستقل. هیچ ادغام دسته‌جمعی شاخه‌های قدیمی.

۲. **حافظه ↔ DIOS ↔ Qwen:** قرارداد رویداد شامل `event_id`، `source_ref`، `observed_at`، `provenance_status`، `decision` و `receipt_hash` تعریف شود؛ مدل فقط پیشنهاد `UNVERIFIED_DRAFT` تولید کند؛ اعتبار تصمیم صرفاً از شواهد و آزمون بیرونی به دست آید؛ هیچ اجرای خودکار patch.

۳. **بدن ↔ روایت ↔ ریچوال:** لینک نسخه‌دار به هندسهٔ سه‌انگشتی و آزمون تعادل، زمان‌بندی تمرین سه‌گانه، و تولید پیشنهاد هنری اضافه شود، اما داده‌های مصنوعی بدن با telemetry واقعی مخلوط نشوند. چهره و تصاویر به‌تنهایی اثبات عملکرد بدن نیستند.

۴. **بقا و گسترش:** خروجی یکپارچه باید روی میزبان مستقل نیز از نسخهٔ بازیابی‌شده تکرار شود؛ رسید restore، مدل/محیط آفلاین و جدایی حوزهٔ خرابی، از شرط‌های عبور هستند. تا آن زمان `PARTIAL_NOT_LIVE_INTEGRATED` وضعیت درست است.

## معیار پذیرش / بازگشت

- تمام آزمون‌های مصنوعی fail-closed در GitHub Actions موفق شوند و در صورت تغییر schema با صدای بلند شکست بخورند.
- **adapter** هیچ پایگاه ناموجود، جدول، رکورد، سرویس، cron، فرمان Bridge، تماس شبکه یا دسترسی API پولی ایجاد نکند. فایل‌های هماهنگی SQLite WAL/SHM ممکن است ایجاد یا تغییر کنند؛ این رفتار با تغییر محتوای منطقی دفترها متفاوت است.
- سوابق نادرست، symlink، مسیر مهاجرت نامعتبر و دست‌کاری هش با وضعیت `invalid` یا `incomplete` گزارش شوند.
- هیچ دادهٔ خصوصی/کلید/متن مدل در خروجی JSON چاپ نشود.
- تأیید merge، نصب روی Ubuntu، اتصال امنیتی زنده و بازیابی مستقل باید جداگانه اخذ و آزمون شوند.
- اگر هر شرط شکست خورد، همین PR بازنگری شود؛ هیچ rollback خودکاری روی سرور زنده انجام نشود.

**نتیجه:** یک نقطهٔ مشاهدهٔ مشترک، قابل‌تست و غیرمخرب ساخته می‌شود. «یکپارچگی زیستی/شناختی» و اجرای سرتاسری هنوز هدف پژوهشی‌اند و ادعای تحقق‌شان نادرست است.
