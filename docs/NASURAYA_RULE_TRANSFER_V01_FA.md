# وقتی دو رسید به یک تجربه برمی‌گردند

۸ نوامبر ۲۰۲۶ | آزمایش حافظهٔ ناسورایا، در ادامهٔ [اولویت شناخت و حافظه](https://github.com/zurvanproject/zohraya/issues/165)

آیا یک تجربهٔ موفق کافی است تا ناسورایا در موقعیتی تازه همان تصمیم را بگیرد؟ در این آزمایش، شرط قراردادی این است که برای تأیید یک ادعای مشخص، دست‌کم دو اجرای اصلیِ جدا نتیجهٔ همسو داشته باشند. رویارویی با یک نتیجهٔ مخالف، تعمیم را متوقف می‌کند. این آستانه یک انتخاب طراحی است.

## خطایی که بازتولید شد

در [نسخهٔ قبلی](https://github.com/zurvanproject/zohraya/blob/5cd91961eef39a2a6a3f1a2a470b8068a914812e/examples/nasuraya_research/rule_transfer_core.py)، شمارش با نشانی رسید انجام می‌شد. در یک ورودی ساختگی از روی دو نشانی واقعی، اجرای بازیابی و بازخوانی سردِ همان نتیجه باعث شد بانک قاعده دو شاهد بشمارد و دستور بازیابی از منبع را برای دارایی تازه توصیه کند. در نسخهٔ اصلاح‌شده، نتیجهٔ همان ورودی «درخواست بازبینی» است. اگر در همان قالب، دو اجرای اصلی با منشأ جدا بدهیم، بازیابی از منبع انتخاب می‌شود.

نسخهٔ جدید شناسهٔ اجرای اصلی و نوع مشاهده را ثبت می‌کند. برای یک ادعا، اجرای اصلی رأی دارد. بازپخش و نسخهٔ تکراری برای ردگیری می‌مانند. آزمون‌های ناسازگاریِ شناسه و تغییر رکورد بعد از ورود، از تبدیل شواهد مبهم به توصیه جلوگیری می‌کنند. مشخصات [OpenLineage](https://github.com/OpenLineage/OpenLineage/blob/main/spec/OpenLineage.md) نیز برای چند رویداد مربوط به یک اجرا شناسهٔ مشترک در نظر می‌گیرد. قاعدهٔ رأی‌گیریِ این پروژه را خودمان تعریف کردیم.

## مواجهه با ده رسید واقعی

آداپتورِ فقط‌خواندنی، یک تصویر ثابت از ده رسید [پروژهٔ حافظهٔ عمومی](https://github.com/zurvanproject/zohraya/pull/169) را با SHA-256 بررسی می‌کند. فرمان، حالت اجرا، شروط نتیجه و اثرانگشت مشترک هر جفت را می‌خواند. کدِ بایگانی‌شده نشان می‌دهد [بازیابی](https://github.com/zurvanproject/zohraya/blob/8da7df54e63d7ac7970f87f8457e322a6c0d7f05/tools/bridge_jobs/moltbook_recovery_run.py#L139-L145) از مشاهدهٔ قبلی استفاده کرده و [آزمون تعمیر](https://github.com/zurvanproject/zohraya/blob/1987da5fc5ebed18cb43372b6ea776b0b4804629/tools/bridge_jobs/moltbook_repair_retest.py#L71-L89) همان سابقهٔ بازیابی را منشعب کرده است.

| ادعای مورد بررسی | نشانی رسید | اجرای اصلیِ قابل‌شمارش برای همان ادعا |
|---|---:|---:|
| ذخیرهٔ یک مشاهدهٔ عمومی | ۲ | ۱ |
| تصمیم به انتظار هنگام ثابت ماندن گفت‌وگو | ۲ | ۱ |
| تغییر رفتار در کنترل با پیامد ساختگی | ۲ | ۰ |
| بازیابی یک نسخه پس از ایجاد خرابی | ۲ | ۱ |
| خواندن محلی پس از تعمیر و بازبینی اجباری | ۲ | ۱ |

این پنج ادعا مستقل از هم امتیاز می‌گیرند. برای نمونه، یک بار بازیابی موفق ثبت شده و فرایند دیگری همان رسید را دوباره خوانده است. هیچ‌کدام از پنج ردیف به آستانهٔ تعمیم نرسید. ## آزمون‌های مقایسه‌ای

دوازده حالت ساختگی و پاسخ‌هایشان در پروندهٔ ثابت `docs/evidence/rule-transfer-lineage/holdout.json` پیش از اجرای کد جدید ثبت شدند. نویسندهٔ این مجموعه تعریف مسئله را می‌دانست و پیاده‌سازی را ندیده بود. شمارش همهٔ نشانی‌های تأییدشده با همان شرط آستانه و تعارض، ۸ پاسخ درست و ۴ انتخاب بی‌پشتوانه داشت. همیشه خودداری کردن ۷ پاسخ درست داد. روش جدید ۱۲ پاسخ درست و صفر انتخاب بی‌پشتوانه داشت. این ۱۲ حالت به‌تنهایی سهم جداگانهٔ حذف بازپخش و تشخیص منشأ مشترک را تعیین نمی‌کنند. آزمایش تکمیلی «دو نشانی برای یک اجرای اصلی» اثر شناسهٔ مشترک را مستقیم می‌سنجد.

در آزمایش فایل، سه محتوای جدا ساختیم و هر سه فایل کاری را عمداً تغییر دادیم. SHA-256 هر سه تغییر را نشان داد. دو نسخهٔ پشتیبان سالم، محتوای اصلی را دقیقاً برگرداندند. در سومی، پشتیبان را هم خراب کردیم و کپی کردن آن به بازیابی منجر نشد. یک موفقیت همراه با دو نسخهٔ رسیدش یک شاهد ماند. دو بازیابی واقعی بر دو فایل جدا برای تأیید کافی بود. با اضافه شدن شکست سوم، ناسورایا درخواست بازبینی کرد. این‌ها اجرای محلی روی فایل آزمایشی هستند.

در مجموعهٔ قبلی، ۱۵ رکورد از ۱۸ رکورد ساختگی پذیرفته می‌شوند. در ۳۰ موقعیت تازه، سیاست بدون حافظه ۷، یادآوری همان دارایی ۱۱، بازبینی همیشگی ۱۶ و بانک قاعده ۳۰ پاسخ درست داشتند. قالب داده با افزودن شناسهٔ منشأ تغییر کرد. هش پیشین `97b2e9f8bfa5b0ba27f8d124591b7418d970060471cc880d2823a7b15d6a343f` و هش جدید `f0b1a0373a2ae2786d1c7ed41938e291391ba3832cc8616abbbe0124f6e5cfce` است.

## بازتولید

از ریشهٔ مخزن با پایتون ۳.۱۰ یا بالاتر اجرا کنید.

```bash
python -m unittest discover -s tests -p 'test_rule_transfer_probe_v01.py' -v
python -m unittest discover -s tests -p 'test_*lineage.py' -v
python -m examples.nasuraya_research.rule_transfer_probe_v01
python -m examples.nasuraya_research.public_receipt_lineage
python -m examples.nasuraya_research.lineage_file_control
```

شناسه‌های اجرای اصلی در مجموعهٔ ساختگی داده شده‌اند. تفسیر رسیدهای عمومی به همین قالبِ بازرسی‌شده محدود است. دو اجرای جدا همچنان می‌توانند خطای نرم‌افزاری مشترکی داشته باشند. این آزمایش به‌روزرسانی نرم‌افزار پژوهشیِ شاخهٔ پیش‌نویس است. معیارش تصمیم قابل مشاهدهٔ نرم‌افزار است.

## استخراج خودکار منشأ از GitHub Actions

برای قالب عمومی GitHub، مبدل `github_job_lineage.job_evidence` شناسهٔ اجرای اصلی را از رکورد خود GitHub استخراج می‌کند. مخزن عمومی، SHA، شماره و نوبت اجرای گردش‌کار، مسیر فایل گردش‌کار، نام کارهای مورد نظر و نشانی‌های API را بررسی می‌کند. دو گزارش از همان شناسهٔ job هنوز یک شاهدند. در [اجرای آرشیوی گالری](https://github.com/zurvanproject/zohraya/actions/runs/42475628332)، job اوبونتو از دو مسیر API بازیابی شد. با افزودن job ویندوز، دو اجرای موفقِ جدا ثبت شد. هر دو همان کد پروژه را آزمودند.

برای آزمون تازه، پیش از ایجاد نسخهٔ دارای مبدل، شمارهٔ نوبت، رویداد push، نام گردش‌کار، دو کارِ هدف و رفتار مورد انتظار در [پروتکل](evidence/rule-transfer-lineage/job-protocol.txt) تعیین شد. این نمونه جدا از آزمون‌های گالری است. مبدل در آزمایش آفلاین کار می‌کند و تهیهٔ رکورد معتبر از API رسمی بر عهدهٔ فراخواننده است. [خروجی‌های مرحلهٔ اول](evidence/rule-transfer-lineage/results.json)

## بازخوانی پس از بستن فرایند

هفت فرایند جداگانه یک دفتر آزمایشی مشترک را باز می‌کنند. بازخوانی‌ها همیشه به رسید اول برمی‌گردند. گام دومِ بازیابی روی فایل مستقلی انجام می‌شود و گام شکست، یک پشتیبان عمداً خراب دارد. برای تکرار محلی، از ریشهٔ مخزن در یک محیط Bash با مسیر موقت تازه اجرا کنید. خود فایل‌ها و رسیدها در آن مسیر باقی می‌مانند.

```bash
trial_dir="$(mktemp -d)"
for step in first replay_one replay_two second replay_three failed replay_final
do
  PYTHONPATH=. python docs/evidence/rule-transfer-lineage/cold_readback.py "$trial_dir" "$step" || break
done
PYTHONPATH=. python docs/evidence/rule-transfer-lineage/verify_cold_readback.py "$trial_dir" "$trial_dir/results.json"
```

در تکرار محلی می‌توان گام‌ها را بی‌فاصله اجرا کرد. بررسیِ پایانی از روی رسیدهای اصلی و فایل‌های روی دیسک تصمیمِ هر مرحله را دوباره محاسبه می‌کند. زمان‌ها و شناسه‌های فرایند مشاهدهٔ محلی‌اند. نسخهٔ جدید هر بار شناسه‌های تازه می‌سازد. [رسید آزمون دو سیستم‌عامل](evidence/rule-transfer-lineage/hosted-job-check.json)

در اجرای زمان‌دار از ۲۳:۲۱ تا ۲۳:۳۲ تهران، دفتر هفت بار در فرایندهای مجزا باز شد. پس از یک بازیابی و دو بازخوانی، شمار اجرای موافق یک بود. با بازیابی دوم به دو رسید. یک بازخوانی دیگر آن را روی دو نگه داشت. شکست بازیابی سوم و سپس آخرین بازخوانی، هر دو «دو موافق، یک مخالف، نیاز به بازبینی» دادند. روی کپی جداگانه، افزودن یک بایت به رسید باعث رد بازخوانی شد. [دفتر زمان‌دار و سه رسید اصلی](evidence/rule-transfer-lineage/cold-session.json)
