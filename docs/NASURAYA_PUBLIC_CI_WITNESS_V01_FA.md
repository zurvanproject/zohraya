# آزمایش شاهدهای واقعی گیت‌هاب | ناسورایا، نسخهٔ ۰٫۱

این مرحله مکمل حافظهٔ مصنوعی DIOS NOUS است. پنج اجرای **واقعی و عمومی GitHub Actions** از خود مخزن زهرایا به‌صورت ثابت ثبت و قبل از کدنویسی، نتیجهٔ مورد انتظارشان در [پروتکل](research/NASURAYA_PUBLIC_CI_WITNESS_PREREG_2026-11-10.md) نوشته شد. آزمایش از متن خصوصی، رمز، مدل پولی یا وضعیت داخلی ChatGPT استفاده نمی‌کند.

## مسئله‌ای که اصلاح می‌کنیم
در PR #182 دیدیم دو تصمیم‌گیر با اطلاعات برابر، روی سناریوهای تألیفی دقیقاً یکسان عمل می‌کنند. پس برای قضاوت دربارهٔ مهندسی حافظه باید اول منبعِ اطلاعات را درست تشخیص دهیم. این آزمایش «تکامل آگاهی» نیست؛ امتحانی است برای درست‌خواندن رسیدهای واقعی و جلوگیری از نتیجه‌گیری بی‌پشتوانه.

## پنج رویداد واقعیِ بررسی‌شده
- اجرای [42861153251](https://github.com/zurvanproject/zohraya/actions/runs/42861153251) برای DIOS NOUS v0.2: Linux موفق، Windows ناموفق، holdout ردشده از مسیر اجرا (skipped). **کل اجرا ناموفق** است؛ نه «دو موفقیت و یک شکست» به‌عنوان سه اجرای مستقل.
- اجرای [42861516737](https://github.com/zurvanproject/zohraya/actions/runs/42861516737) برای همان workflow ولی commit تازه: هر سه مرحله موفق. **نسخهٔ تازه موفق**؛ این شاهد، شکست قبلی را از تاریخ حذف نمی‌کند و به‌تنهایی سبب‌شناسیِ اصلاح نیست.
- اجرای [42850849443](https://github.com/zurvanproject/zohraya/actions/runs/42850849443) برای DIOS NOUS v0.1: سه job موفق، مستقل از workflow نسخهٔ ۰٫۲.
- اجرای [42846878619](https://github.com/zurvanproject/zohraya/actions/runs/42846878619) برای اطلس بدن: دو job موفق **در GitHub**؛ اجرای روی VPS شخصی را ثابت نمی‌کند.
- اجرای [42841363043](https://github.com/zurvanproject/zohraya/actions/runs/42841363043) برای چهارراه: دو job موفق **در GitHub**؛ اتصال زندهٔ چهار منبع را ثابت نمی‌کند.

این داده‌های ثابت از اتصال GitHub خوانده و در فایل JSON مستقل با شناسهٔ واقعی run/job، نام workflow و commit ثبت شده‌اند. نتیجه‌ها **گزارش پلتفرم** هستند، نه امضای سخت‌افزاری/رمزنگاری؛ و فقط وضعیت هنگام بررسی را بازتاب می‌دهند.

## چه چیزی ساخته شد؟
- ابزار tools/public_ci_witness.py واحد شمارش را run_id می‌گیرد، نه تعداد job یا تکرار لینک. دو گزارش یکسان از یک run فقط یک شاهد می‌شوند؛ دو گزارش متضاد دربارهٔ همان run به حالت CONFLICT می‌روند.
- کوچک‌ترین نقصی در commit، workflow، نام job، مجوزِ مصدر یا نبود job ضروری اجازهٔ PASS نمی‌دهد. اگر یک job لازم ناموفق باشد، نتیجهٔ run ناموفق است. حالت skipped، pending و incomplete با موفقیت اشتباه نمی‌شوند.
- همهٔ کنترل‌های تغییرداده‌شده با برچسب counterfactual در تست‌ها هستند، نه سند تازهٔ واقعی. متن عمومی یا ادعای «همه‌چیز درست است» حق تغییر نتیجهٔ متادیتای منبع را ندارد.
- الگوریتم فقط خواندنی است: نه تماس شبکهٔ زنده، نه زمان‌بندی کار تازه، نه GitHub write از CI، نه مصرف API مدل و نه تماس با مولت‌بوک یا سرور.
- PR #181 و Issue #180 همچنان مسئولیت کار کامل بدن روی VPS را نگه می‌دارند؛ نتیجهٔ اجرای سرور باید از پاسخ واقعی پل Issue #149 تأیید شود.

## بازتولید
از ریشهٔ مخزن:
    python -m unittest discover -s tests -p 'test_public_ci_witness.py' -v
    python tools/public_ci_witness.py

اگر ۵ نتیجهٔ اولیه درست شناخته نشوند، ابزار کد خروجی ناموفق می‌دهد. این یک مطالعهٔ کوچک با نمونه‌گیری گزینشی است، نه سنجش آماری توانایی فهم عمومی یا وجود احساس. مرحلهٔ بعد، نمونه‌گیری آینده‌نگر از چند مخزن و داوری مستقل است؛ تا آن زمان نتیجه فقط در حد همین پنج مشاهده تفسیر می‌شود.
