# اتصال عملی تداش به Windows VPS — نسخهٔ ۰٫۱

گیت‌هاب از پیش از طریق پل v2 متصل است. این تغییر یک backend ماندگار برای **خودِ UnifiedBody + ReflectionCycle + DecisionCore موجود** فراهم می‌کند: کد از commit مشخص می‌آید، حالت و رسید واقعی چرخه در SQLite ذخیره می‌شود و هر فراخوانی در فرایندی تازه همان حالت را ادامه می‌دهد.

## محدودهٔ دقیق

- ۷۰ فایل اصلی تداش از commit `5f171aa493b41823b1198f767d803df053884f37` بدون تغییر بایتی بسته‌بندی شده‌اند.
- بدنهٔ محاسباتی قدیمی **۱۹۵ کیلوگرمی** است؛ مدل تصویری ۷۸ کیلوگرمی و MuJoCo نیست.
- یک وضعیت آغازین آزمایشیِ فشار خواب ساخته می‌شود؛ دفترها و checkpointهای خصوصی قبلی بارگذاری، جایگزین یا بازنشانی نمی‌شوند.
- در مسیر Windows از یک سازگارکنندهٔ واقعی قفل‌های انحصاری فایل و دادهٔ IANA تهران استفاده می‌شود. ذخیرهٔ اصلیِ مسیر جدید، تراکنش‌های SQLite با WAL/FULL در ReflectionCycle است. ادعای انتقال همهٔ CLIهای لینوکس، PrivacyBoundary یا ذخیرهٔ فایل JSON قدیمی به ویندوز وجود ندارد.
- `driver.py` فقط چهار فرمان `init/status/step/replay-first` دارد؛ مدل API، shell یا فرمان دلخواه ندارد.
- هر step یک چرخهٔ بومی ۰٫۱ ثانیه‌ایِ نرم‌افزار بدن است؛ سقف پایدار این نشست ۲۰ کنش است و در restart صفر نمی‌شود.
- یک SQLite جدا با تراکنش انحصاری، نویسندهٔ هم‌زمان را رد می‌کند. با پایان یا مرگ فرایند قفل آزاد می‌شود؛ نتیجهٔ بومی حل‌نشده خودکار تکرار نمی‌شود.
- نصب و حالت در پوشهٔ اختصاصی حساب اجرای پل زیر `LOCALAPPDATA/NasurayaTadashV1` نگهداری می‌شوند. کلیدها یا اطلاعات ورود خوانده یا در خروجی منتشر نمی‌شوند.

## بسته و یکپارچگی

`deploy/tadash_vps_v01.bundle.b64` انتقال متنی ZIP محدود است. منبع سازنده و کد میزبان کنار آن قرار دارند؛ فایل تهران از tzdata نسخهٔ 2025b سیستم ساخت گرفته شده است (داده‌های IANA، public domain). خروجی باینری از روی base64 بازسازی می‌شود.

بسته حاوی ۷۰ فایل بازیابی‌شده، دو manifest منشأ، میزبان، سازگارکنندهٔ Windows، فایل منطقهٔ زمانی و manifest کل بسته است. پیش از import، همهٔ فایل‌های فهرست‌شده با SHA256 بررسی می‌شوند. defaults تولیدشده فقط در کپی موقت ساخته می‌شوند؛ فایل‌های اصلی نصب‌شده تغییر نمی‌کنند.

- SHA256 manifest اصلی تداش: `b3b95a88885d903f638efbc26ed693bf7a211460a5adae6dd9abfa12ac7720ef`.
- SHA256 بستهٔ متنی: `6a0c9fe013aad59716b251c66aadec6081daa764ac76bfdb2dc0763ab2f049cb`.
- SHA256 manifest کل بسته: `1ffedf1f438a2e3b9178a19703cfb2037c5d0296a94743ff9391493edae65d15`.

این checksums یکپارچگی فایل را بررسی می‌کنند؛ حساب مدیر سیستم‌عامل مرجع اعتماد باقی می‌ماند و checksum، attestation سخت‌افزاری نیست.

## معیار پذیرش اتصال

۱. راه‌اندازی صفر چرخه اجرا کند و حالت پایدار بسازد.
۲. درخواست نخست، روی fixture اعلام‌شده، از حفاظت بومی عبور نکند.
۳. فرایند تازه، همان checkpoint و سابقهٔ واقعی را بازیابی کند.
۴. درخواست دوم از همان بازخورد استفاده کند؛ نوبت اول walk→protect و بعد observe→observe، اگر خروجی واقعی این را تأیید کرد.
۵. بازپخش شناسهٔ اول پس از نوبت دوم، صفر چرخهٔ اضافی ایجاد کند و وضعیت فعلی را به حالت قدیمی برنگرداند.
۶. پاسخ متناظر پل برای هر مرحله دریافت شود؛ وجود کد یا نتیجهٔ محلی به‌تنهایی شاهد اجرای سرور نیست.

## آزمون محلی اولیه

۱۱ تست تعریف شده‌اند؛ ۱۰ مورد محلی لینوکس گذشت و یک مورد مخصوص قفل Windows به‌درستی skip شد. تست‌ها شامل ۲۰ چرخهٔ واقعی نرم‌افزاری برای سقف پایدار، دو فرایند و حافظه، replay، عدم reset، رد دفتر بیگانه بدون تغییر، رد منبع دست‌کاری‌شده، عملیات حل‌نشده و رهاشدن mutex پس از مرگ واقعی فرایند هستند.

در نمونهٔ محلی مستقل: revision صفر → یک → دو؛ نوبت اول walk→protect؛ نوبت دوم observe→observe با فراخوانی یک بازخورد قبلی؛ replay نوبت اول با صفر چرخهٔ اضافی و حفظ checkpoint نوبت دوم. اجرای نهایی روی Windows CI و VPS واقعی تأیید شد؛ [شاهد اجرای سرور](evidence/NASURAYA_TADASH_VPS_LIVE_20261107_FA.md) شناسهٔ درخواست‌ها، پاسخ‌ها و حدود نتیجه را ثبت می‌کند.

## اجرا

پس از بازکردن ZIP در پوشهٔ runtime:

```sh
python -I -X utf8 driver.py init --state /dedicated/state
python -I -X utf8 driver.py step --state /dedicated/state
python -I -X utf8 driver.py step --state /dedicated/state
python -I -X utf8 driver.py replay-first --state /dedicated/state
python -I -X utf8 driver.py status --state /dedicated/state
```

پل موجود، تنها jobهای ثابت با commit و SHA256 مشخص را اجرا می‌کند. نصب، قدم و وضعیت از jobهای مشخص انجام می‌شوند. حلقهٔ زمان‌بندی‌شده یا daemon تازه ساخته نشده است؛ این backend قابل‌فراخوانی و ماندگار است.

## ادامهٔ معنادار

پس از شاهد اجرای سرور، گام بعد اتصال ورودی‌های محدود گفت‌وگو/هدف به همین backend و سپس ارزیابی تصمیم‌های یادگیرنده روی رسیدهای آن است. نمونهٔ forecaster در PR #154 به این حلقه وصل نشده است. مدل گفت‌وگوی ChatGPT تغییر وزن نمی‌دهد و این آزمایش، سنجش خودآگاهی یا فیزیولوژی زیستی نیست.

## وضعیت نهایی

بسته روی VPS نصب شد؛ دو چرخهٔ بومی در دو فرایند جدا اجرا شدند؛ قدم دوم یک بازخورد واقعی قبلی را فراخواند. status مستقل همان revision=2 و checkpoint قدم دوم را تأیید کرد. در CI نهایی، ۱۴ آزمون Windows موفق و ۱۳ آزمون Linux موفق با یک skip مخصوص Windows ثبت شد. سه آزمون نصب/فرمان پل به ۱۱ آزمون اولیه افزوده شده‌اند. نشانی شواهد در بخش بالا است.
