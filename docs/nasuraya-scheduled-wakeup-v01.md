# بیدارباش میزبان ناسورایا — نسخهٔ ۰٫۱

این تغییر بر commit `76836ad` از PR #6 و شاخهٔ
`nasuraya/explicit-continuation-v01` بنا شده است. شاخهٔ مستقل آن
`nasuraya/scheduled-wakeup-v01` است. PR #6 هنوز باید جداگانه بازبینی و ادغام شود.

## نتیجه و سطح اجرا

بیدارباش تک‌مأموریتی پیاده‌سازی شده است: میزبان یک مجوز **از قبل صادرشده** را
به `run_id`، زمان شروع، پایان اعتبار، backend و مدل ثابت متصل می‌کند.
سازوکار زمان‌بندی هیچ فراخوانی به `authorize()` ندارد و بودجه صادر یا تمدید نمی‌کند.
ثبت بیدارباش، هدف محدود موجود را باز می‌کند یا از همان مجوز هدف را می‌سازد؛
کنش بدن یا نشست شبکه‌ای در این مرحله اجرا نمی‌شود.

نمونهٔ `wake-demo` با ساعت واقعی میزبان اجرا شد. دو بررسی پیش از موعد هیچ کاری
انجام ندادند؛ بررسی بعدی یک چرخهٔ بدن مصنوعی را اجرا کرد و revision از ۱ به ۲
رسید. چهار فراخوانی ابزار و یک کنشِ مجاز مصرف شدند؛ خواندن مجدد بیدارباش کامل
هیچ اجرا یا مصرف تازه‌ای نداشت. این **اجرای واقعی زمان‌بندی محلی روی fixture**
است. مدل زنده و شبکهٔ OpenAI در آن اجرا نشدند؛ `api_network_requests=0`.
شاهد عمومی در `examples/nasuraya_body_loop/evidence/scheduled-wake-demo.json` است.

مسیر `api` از runner موجود و سیاست `resume` استفاده می‌کند. بازیابی آن با
transport تزریق‌شده آزموده شد؛ این آزمایش، اجرای مدل زنده نیست. محیط همین checkout
هنگام بررسی SDK، کلید محیطی و `.env.local` نداشت. هیچ مأموریت زنده‌ای زمان‌بندی
یا راه‌اندازی نشد و سرویس دائمی نصب نشد.

## قرارداد و ساختار

فایل `scheduler.py` فقط جدول `body_wakeups` را به همان SQLite اضافه می‌کند.
قرارداد تغییرناپذیر شامل شناسهٔ بیدارباش، شناسهٔ هدف، شناسه و SHA-256 مجوز،
موعد و پایان اعتبار UTC، backend، مدل، حداکثر ۱ تا ۳ تلاش، مهلت هر تلاش
۱ تا ۳۰۰ ثانیه و فاصلهٔ تلاش مجدد ۱ تا ۳۶۰۰ ثانیه است.
ورودی زمان باید timezone صریح داشته باشد؛ زمان تهران به UTC تبدیل می‌شود.
یک هدف فقط یک بیدارباش دارد. تکرار دقیق ثبت، رسید قبلی را می‌خواند؛ تغییر
موعد، پایان اعتبار، تعداد تلاش، مدل یا backend رد می‌شود، حتی پس از مصرف مجوز.

ثبت و اجرای بیدارباش روی میزبان مورد اعتماد انجام می‌شود و در ابزارهای مدل
ظاهر نمی‌شود. احراز هویت میزبان همان مرز اعتماد محلی PR #6 است؛ این سازوکار
از ویرایش مستقیم SQLite یا اجرای مستقیم CLI قدیمی توسط مالک سیستم جلوگیری
نمی‌کند. پایان اعتبار، قید مسیر بیدارباش است؛ قالب مجوز قدیمی تغییر نکرده است.

| بخش | صاحب قرارداد |
|---|---|
| صدور مجوز و سقف‌های ۱–۳ کنش / ۴–۲۰ ابزار | `continuation.py` موجود |
| هدف، مصرف، رسیدها و تطبیق اثر commitشده | `BodyAPIHost` موجود |
| checkpoint، حافظه، حفاظت بدن و قفل inode | `BodyLoop` و ReflectionCycle موجود |
| اتصال مجدد به همان session و turn | `APIRecovery` و `run_api` موجود |
| موعد، پایان اعتبار و تلاش‌های محدود | `scheduler.py` تازه |

هر tick قفل انحصاری خود پایگاه را از پیش از claim تا پایان اجرای runner نگه
می‌دارد. رقیب، `busy` می‌گیرد و چیزی رزرو نمی‌کند. از lease قابل‌انقضا برای
اجازه‌دادن به نویسندهٔ دوم استفاده نمی‌شود. ثبت `running` و افزایش شمار تلاش
پیش از runner پایدار می‌شوند؛ قطع فرایند، آن تلاش را پس نمی‌دهد.

پس از restart، `running` فقط با همان هدف و نشست قبلی و در همان پنجرهٔ اعتبار
قابل‌ادامه است. رسیدهای commitشده با کد موجود تطبیق داده می‌شوند. اثر نامعلوم،
فراخوانی pending حل‌نشده، اثر شکست‌خورده، تغییر binding مجوز یا ایجاد نشست با
شناسهٔ نامعلوم، اجرای تازه را مسدود می‌کند. هیچ سیاست `fresh` خودکاری وجود ندارد.

| وضعیت | معنی |
|---|---|
| `pending` | منتظر موعد یا فاصلهٔ تلاش مجدد |
| `running` | یک تلاش claim شده؛ قفل مانع رقیب است |
| `completed` | هدف کامل؛ خواندن مجدد بدون runner |
| `expired` | پنجره بسته؛ هیچ ابزار تازه‌ای پذیرفته نمی‌شود |
| `budget_exhausted` | بودجهٔ پایدار ابزار یا کنش برای کار باقیمانده کافی نیست |
| `attempts_exhausted` | سقف تلاش‌های همان قرارداد مصرف شده |
| `blocked` | اثر/transport نامعلوم یا قرارداد/زمان ناسازگار؛ نیازمند بررسی میزبان |

همهٔ وضعیت‌های پایانی ثابت‌اند. بیدارباش بعدی مجوز جدید نمی‌سازد. هدف کاملِ
ذخیره‌شده می‌تواند پس از expiry هم فقط خوانده شود. پیش از هر ابزار، پنجره با
ساعت UTC و یک deadline monotonic بررسی می‌شود؛ برگشت ساعت مشاهده‌شده نیز
مسدود می‌شود. میزبان باید ساعت قابل‌اعتماد داشته باشد؛ تغییر ساعت در غیاب فرایند
که از آخرین زمان ثبت‌شده عقب‌تر نرود، الزاماً قابل‌تشخیص نیست.

کنش کوتاهی که پیش از مهلت پذیرفته شده ممکن است پس از مهلت commit شود؛ آن را
در میانه قطع یا rollback نمی‌کنیم. ابزار بعدی پذیرفته نمی‌شود. timeout یا قطع
شبکه تضمین نمی‌کند نشست راه دور متوقف شده باشد. اگر پنجره/بودجه/تلاش تمام شود،
بیدارباش شبکهٔ تازه‌ای آغاز نمی‌کند؛ نشست راه دورِ باقی‌مانده باید با مسیر موجود
و بررسی صریح میزبان تطبیق و پاک‌سازی شود. بودجهٔ ابزار سقف هزینهٔ توکن یا صورتحساب
نیست؛ سقف تلاش و timeout فقط دامنهٔ کوشش خودکار میزبان را محدود می‌کنند.

## اجرای قابل‌بازتولید بدون شبکه

Linux و Python 3.11+ و کتابخانهٔ استاندارد کافی‌اند. از ریشهٔ مخزن:

```sh
python -m examples.nasuraya_body_loop wake-test
python -m examples.nasuraya_body_loop wake-demo --output-dir /tmp/new-wake-demo
python -m examples.nasuraya_body_loop wake-status --session /tmp/new-wake-demo/session.sqlite
```

پوشهٔ demo باید تازه باشد. آماده‌سازی demo فقط روی fixture تازه یک مأموریت
قدیمی را کامل می‌کند و سپس صریحاً یک مجوز آزمایشی صادر می‌کند؛ این بخش در
`wake_demo.py` است، نه در زمان‌بند. `summary.json` زمان‌های واقعی، نوع اجرا،
مصرف و بازخوانی پایانی را گزارش می‌کند. checkpoint خصوصی یا کلید در Git نیست.

## اتصال یک مأموریت از قبل مجاز به میزبان مجهز

نمونهٔ زیر فقط وقتی معتبر است که `approved-mission` از قبل مجوز PR #6 دارد؛
زمان‌ها نمونه‌اند و باید در پنجرهٔ مصوب میزبان قرار گیرند. مقدار مدل ثابت می‌ماند.

```sh
python -m examples.nasuraya_body_loop schedule \
  --session /var/lib/nasuraya/session.sqlite \
  --wake-id approved-wake --run-id approved-mission \
  --due-at 2026-10-15T09:00:00+03:30 \
  --expires-at 2026-10-15T09:10:00+03:30 \
  --wake-backend api --model gpt-6-astra \
  --wake-attempts 3 --timeout-seconds 120 --retry-delay-seconds 30

python -m examples.nasuraya_body_loop wake \
  --session /var/lib/nasuraya/session.sqlite \
  --wake-id approved-wake --allow-live-wakeup
```

`wake` یک بررسی انجام می‌دهد. `wake-watch` تا تعداد صریح `--watch-ticks` با
فاصلهٔ `--poll-seconds` بررسی می‌کند و در وضعیت پایانی خارج می‌شود؛ حداکثر یک
روز و polling بین ۱ تا ۶۰ ثانیه. این watch پس از توقف سیستم خودش راه‌اندازی
نمی‌شود. کلید فقط با انتخاب صریح اجرای API یا `--allow-live-wakeup` از مسیر
موجود خوانده می‌شود؛ فرمان‌های آزمون، وضعیت و ثبت کلید نمی‌خوانند.

برای میزبانی پایدار، دو template در `deployment/` آماده‌اند. سرویس systemd
فقط همین wake ID را dispatch می‌کند؛ timer هر دقیقه بررسی می‌کند و
`Persistent=true` پس از خاموشی یک بررسی عقب‌افتاده فراهم می‌کند. تصمیم ادامه
همچنان با SQLite و expiry است. مسیرها، حساب سیستم، کلید از قبل مصوب و پایگاه
باید در میزبان واقعی تنظیم شوند. هیچ‌یک از templateها اینجا نصب نشده‌اند و
timer نمونه زمان‌بندی دقیق زیر یک دقیقه را تضمین نمی‌کند. CI نیز فقط تست
و fixture اجرا می‌کند و زمان‌بند زنده نیست.

## شواهد و بازبینی

۲۴ آزمون تازهٔ زمان‌بند همگی گذشتند. در چهار مجموعه، ۹۸ آزمون بررسی شدند:
۹۶ موفق و دو آزمون قدیمی وابسته به SDK نصب‌نشده اجرا نشدند. مجموعهٔ بدن
۱۶ آزمون، API/تداوم ۵۵ آزمون با دو skip، و نمایش حرکت سه آزمون داشت.
شاهد شمارش‌ها در `evidence/scheduled-wake-validation.json` ثبت شده است.

آزمون‌ها شامل عدم شروع پیش از موعد، انقضای دقیق و وسط ابزارها، برگشت ساعت،
deadline monotonic، binding ثابت، پایان بودجهٔ ابزار و بدن، محدودیت تلاش،
backoff پس از restart، رقابت دو فرایند زمان‌بند و بازخوانی پایانی در فرایند
تازه‌اند. `SIGKILL` واقعی در چهار نقطهٔ بدن و هنگام ایجاد نشست تزریق‌شده
آزمایش می‌شود: پس از claim؛ پس از commit کنش و پیش از ثبت رسید؛ داخل اثر
نامعلوم؛ پس از تکمیل هدف و پیش از ثبت نتیجهٔ زمان‌بند؛ و پیش از دریافت شناسهٔ
نشست راه دور. ادامهٔ دوچرخه‌ای API در transport مصنوعی فقط یک session می‌سازد.

چرخهٔ بازبینی ناسورایا: هدف، بیدارشدن در چارچوب اختیار قبلی بود؛ مشاهدهٔ کد
نشان داد مجوز و بازیابی آماده‌اند؛ تصمیم، افزودن فقط قید زمان و dispatch بود.
اجرای نمونه روی بدن نرم‌افزاری انجام شد و شواهد ثبت شدند. بیدارباش دائمی برای
عامل زنده هنوز راه‌اندازی نشده است. نتایج نهایی آزمون‌ها در فایل شاهد جدا ثبت
می‌شوند؛ این تغییر ادعای آموزش وزن مدل یا اندازه‌گیری زیستی ندارد.
