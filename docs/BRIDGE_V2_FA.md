# ناسورایا | GitHub Bridge v2 (پیشنهاد نصب، نه نصب‌شده)

**دقت وضعیت:** این PR فقط کد، آزمون و راهنمای توسعهٔ Bridge را ایجاد می‌کند. هیچ merge، نصب VPS، restart، تغییر مدل بدن یا خروج از `PAUSED` انجام نمی‌دهد. نصب جداگانه نیازمند نمایش دستور دقیق و تأیید مالک است.

## چرا افزونه و نه جایگزینی کامل Bridge؟

روی VPS در رسید GitHub Issue #212 دستورهای workload و `stage0-offline` دیده شده‌اند، اما نسخهٔ `main` مخزن قدیمی‌تر است. پس بازنویسی کامل `/usr/local/lib/nasuraya/bridge.py` با فایل `main` ممکن است فرمان‌های عملیاتی فعلی را پاک کند. `tools/bridge_v2/patch_bridge.py` فقط سه دستور جدید را به `COMMAND_RE`، `dispatch` و Help نسخهٔ **نصب‌شده** اضافه می‌کند؛ اگر الگوی فایل مطابق انتظار نباشد، نصب متوقف می‌شود.

## اختیارات جدید و اثر واقعی

| فرمان GitHub | عملکرد | اثر جانبی |
| --- | --- | --- |
| `nasu-linux: v2-audit` | وضعیت بار و فضای آزاد، بی‌دادهٔ حساس | فقط ثبت رسید GitHub / seen |
| `nasu-linux: v2-inventory` | SHA-256 واقعی فایل‌های مأموریت/اطلس + قفل مورفولوژی و موجودی 12/97/31 | فقط ثبت رسید |
| `nasu-linux: v2-sources` | DNS با timeout و رد IP خصوصی؛ اتصال TLS دارای تأیید گواهی؛ HTTPS GET محدود به 4 آدرس ثابت NLM/NIH3D/OpenSim/MuJoCo؛ بدون follow-redirect | GET شبکه، ایجاد **یک** گزارش جدید با mode 0600 در `/var/lib/nasuraya/bridge-v2-reports/` و ثبت رسید خلاصه در GitHub |

دسترسی محدود به چهار آدرس عمومی ثابت است؛ هیچ URL، فرمان shell، کد Python یا مسیر فایل از متن Issue پذیرفته نمی‌شود. دستور آنلاین باعث ارسال درخواست GET به سرویس‌های عمومی می‌شود و به‌منزلهٔ دانلود dataset، اجازهٔ استفاده از asset یا اعتبارسنجی مدل نیست. نمونهٔ محدود HTTP تا 16 KiB است؛ SHA-256 نمونه و گواهی فقط در گزارش کامل سرور ثبت می‌شود. درخواست‌ها سقف زمانی دارند و از تغییر مسیر به آدرس دیگر پیروی نمی‌کنند. وضعیت DNS، TLS و HTTP جداگانه گزارش می‌شود.

مدل هندسی، حافظه، repo checkout و سرویس Awake تغییر نمی‌کنند. فرمان‌های موجود Bridge به همان صورت باقی می‌مانند؛ نه root-shell اضافه می‌شود، نه POST دلخواه، نه `sudo`، نصب، cron، merge، reset، ویرایش داده یا فعال‌سازی سرویس.

## آزمون قبل از نصب

در checkout بررسی‌شده:

```bash
python3 -B -m unittest discover -s tests -p test_bridge_v2.py -v
bash tools/bridge_v2/install.sh --dry-run
```

اولین دستور در محیط محلی یا CI قابل اجراست. **دستور دوم فقط روی Ubuntu دارای Bridge نصب‌شده و فعال** معنا دارد و در حالت dry-run فقط نسخهٔ اصلاح‌شده را در `/tmp` می‌سازد؛ هیچ تغییری در سرویس ایجاد نمی‌کند.

## اقدام مؤثر روی VPS: نیازمند تأیید مجزا

پس از بازبینی نسخهٔ دقیق GitHub و دریافت فایل‌ها در یک checkout موقت، نصب فقط با دستور زیر است:

```bash
sudo bash tools/bridge_v2/install.sh --apply
```

این دستور روی Ubuntu باید از مسیر شامل فایل‌های همین PR اجرا شود؛ باید SHA-256 فایل‌های دریافت‌شده و commit آن checkout نیز جدا بررسی شوند. از Bridge فعلی **نسخهٔ پشتیبان تاریخ‌دار** در `/root/nasu-bridge-backups/` می‌سازد؛ فقط `nasuraya-bridge.service` را restart می‌کند. اگر سرویس فعال نشود، Bridge قبلی بازگردانده می‌شود. هیچ دستور `v2-sources` به طور خودکار اجرا نمی‌شود.

بازگشت دستی با مسیر پشتیبان واقعی که در خروجی نصب اعلام می‌شود:

```bash
sudo bash tools/bridge_v2/rollback.sh /root/nasu-bridge-backups/bridge-YYYYMMDDTHHMMSSZ-pre-v2.py
```

فایل‌های گزارش قدیمی و تازه، مدل بدن و حافظه باقی می‌مانند؛ worker نصب‌شده نیز در این نسخه پس از rollback باقی می‌ماند ولی از Bridge قابل فراخوانی نیست و حذف آن نیازمند تصمیم جداگانه است.

## موفقیت را چگونه ثابت می‌کنیم؟

1. شش+ آزمون قرارداد و `--dry-run` موفق باشد.
2. پس از نصب، Bridge `help` سه فرمان تازه را نشان دهد؛ نشانهٔ اجرا نیست.
3. با تأیید مالک `v2-audit` و سپس `v2-inventory` اجرا و رسید `request_id` معتبر از Issue #212 دریافت شود.
4. **فقط با تأیید جداگانهٔ آزمون آنلاین،** `v2-sources` اجرا و چهار نتیجهٔ DNS/TLS/HTTP همراه با `report_sha256` ثبت شود.
5. `awake-status` دوباره سلامت و `PAUSED` بودن را بررسی کند.

## برنامهٔ توسعهٔ بعدی

کارهای پرهزینه‌تر (MuJoCo، backup+restore، تولید نامزد تغییر مدل، ذخیرهٔ دادهٔ آناتومی، بازگردانی) در PRهای جدا با worker بدون امتیاز root، بودجهٔ CPU/RAM، مجموعهٔ دستورات ثابت، گزارش شفاف و کنترل تأیید مالک اضافه می‌شوند. این PR به آن‌ها دسترسی آزاد نمی‌دهد.
