# بازیابی سازگار حافظهٔ نشست‌های قدیمی — ۲۷ اکتبر ۲۰۲۶

این افزوده بر head آزموده‌شدهٔ PR #67، یعنی `6281c5389b5a7a75d4bf6c6505a24699c98beb70` ساخته شده است. مسیر موفق گفتگو → پیش‌بینی → بدن → یادگیری بازسازی نشده؛ `body_dialogue.py`، `experience.py`، `host.py`، منابع بومی بدن و آزمایش پولی دست‌نخورده‌اند. بنابراین افزودن این ابزار، هش اتصال فعال نسخهٔ سوم را عوض نمی‌کند.

## نتیجه و مرز پیاده‌سازی

**بازیابی خواندنی میان نسخه‌ها اکنون پیاده شده است. انتقال وضعیت اجرایی میان نسخه‌ها پیاده نشده است.** نشست قدیمیِ شناخته‌شده را می‌توان بدون بازکردن موتور اجرایی آن، همراه WAL خواند، اعتبارسنجی کرد، به آرشیوی دارای چکیده تبدیل کرد و پیام/رسید/تجربهٔ آن را در مسیر فرمان یکپارچه بازخواند. عبارت `history-replay` صرفاً بازخوانی دقیق پاسخ تاریخی است؛ هیچ تابع حرکت، یادگیری، تکمیل پیام یا فراخوانی مدل را اجرا نمی‌کند.

نشست تازه همچنان صریح ساخته می‌شود. فراخواننده می‌تواند خروجی `history-recall` را به‌عنوان زمینهٔ تاریخی بخواند. این خروجی خودکار به انتخاب اقدام، وضعیت عاطفی یا `nearest_episode` نشست تازه تزریق نمی‌شود. چنین تزریقی نیازمند قرارداد مستقل سازگاری مدل، شناسهٔ سراسری نشست و جلوگیری از اجرای دوباره در چند نشست است. این تغییر شنوندهٔ ChatGPT یا کارگر پس‌زمینه نمی‌سازد.

| رسید کامل، پیوند صحیح، checkpoint سالم | نتیجهٔ تاریخی با منشأ اصلی خوانده می‌شود؛ صفر چرخهٔ جدید. |
| پیش‌بینی و تجربهٔ سالم در نسخهٔ سوم | مقادیر ذخیره‌شده و منشأ، پس از تطبیق با رسید و سابقه، خوانده می‌شوند؛ هیچ update آموزشی انجام نمی‌شود. |
| نسخهٔ قدیمی بدون تجربه/پیش‌بینی | پیام و رسیدِ موجود بازیابی می‌شوند؛ forecast، prediction و stored_episode برابر null می‌مانند. |
| قطع پس از ثبت نتیجهٔ بدن و پیش از ثبت پاسخ گفتگو | وضعیت `receipt_recovered_not_reexecuted`؛ نتیجهٔ موجود خوانده می‌شود، پاسخ یا تجربهٔ غایب در مبدأ ساخته نمی‌شود. |

| schema/هش ناشناخته، خرابی، جفت نادرست، گسست منشأ یا شناسه، یا completion بدون رسید اندازه‌گیری‌شده | کل snapshot با `archive_only` و علت مشخص نگه داشته می‌شود؛ بازیابی معتبر از آن ادعا نمی‌شود. |
| دفتر تک‌فایلی، یادداشت متنی، API session، ژنوم، بانک خاطرهٔ فاقد پیوند به این پل | این adapter واردشان نمی‌کند؛ نیاز به بررسی و adapter جدا دارند. |
| mood، predictor parameters، خلاصه/فرضیه، checkpoint فعال، بودجه، مجوز | در snapshot خام محفوظ‌اند؛ به نشست تازه منتقل یا به شواهد تازه ارتقا نمی‌یابند. |

اعتبارسنجی، **سازگاری داخلی و منشأ نرم‌افزاری** را بررسی می‌کند؛ دفترهای قدیمی امضای مستقل یا شناسهٔ UUID سراسری ندارند. کسی که همهٔ فایل‌های مبدأ را کنترل کند می‌تواند چکیده‌ها را دوباره بسازد. چکیدهٔ مستقلِ هنگام export برای تشخیص تغییرات پس از export لازم است؛ آن هم اصالت گذشته یا صحت ادعای انسانی را اثبات نمی‌کند.

`historical_id` از `<archive_sha256>/<message_id>` ساخته می‌شود تا IDهای محلی یکسان در آرشیوهای مختلف یکی فرض نشوند. `source_binding_id` فقط اثرانگشت binding قدیمی است، نه UUID یکتای جهانی. export جدید ممکن است archive ID تازه داشته باشد؛ ادغام و حذف تکرار میان چند آرشیو خودکار نیست.

## استفادهٔ صریح

ابتدا همهٔ نویسندگان نشست قدیمی را متوقف کنید. ابزار قفل موجود بدن و قفل موجود affect را به ترتیب می‌گیرد؛ قفل جدیدی در مبدأ نمی‌سازد. نبود قفل affect یا اشغال بودن قفل باعث رد درخواست می‌شود. API مستقل AffectiveAgent که قفل پل را رعایت نکند نیز باید خاموش باشد.

```bash
# فقط بررسی؛ هیچ فایل مقصد یا تغییر نشست ایجاد نمی‌کند.
python -m nasuraya dialogue history-inspect --session-dir /path/to/old-session

# مقصد باید خارج از پوشهٔ نشست باشد و از قبل وجود نداشته باشد.
python -m nasuraya dialogue history-export \
  --session-dir /path/to/old-session --output /path/to/archives/history.json
```

چکیدهٔ `archive_sha256` را از خروجی export جدا نگه دارید. برای همهٔ خواندن‌های بعدی همان مقدار لازم است؛ آن را از نسخهٔ تازه و بررسی‌نشدهٔ فایل نگیرید.

```bash
python -m nasuraya dialogue history-trace \
  --archive /path/to/archives/history.json --expected-sha256 "$ARCHIVE_SHA256" \
  --message-id first

python -m nasuraya dialogue history-recall \
  --archive /path/to/archives/history.json --expected-sha256 "$ARCHIVE_SHA256" --cue body

# JSON دقیق پیام اصلی؛ ID جدید یا محتوای متفاوت رد می‌شود.
python -m nasuraya dialogue history-replay \
  --archive /path/to/archives/history.json --expected-sha256 "$ARCHIVE_SHA256" \
  --message /path/to/original-message.json
```

کد خروج صفر یعنی خواندن معتبر، ۲ یعنی snapshot فقط آرشیو، و ۱ یعنی درخواست رد شده/خطای ورودی یا I/O. `history-recall` از cueهای صریح موجود `body` و `dialogue` استفاده می‌کند؛ جست‌وجوی معنایی تازه اضافه نشده است. پردازش دوبارهٔ همهٔ آرشیو برای هر خواندن، انتخاب محافظه‌کارانهٔ این نسخه است؛ سقف هر فایل و آرشیو ۶۴ MiB و هر جدول ۱۰هزار ردیف است.

SQLite روی **کپی خصوصی** از DB و WAL خوانده می‌شود؛ مبدأ در حالت read-write باز نمی‌شود و SHM نیز فقط در کپی موقت ساخته می‌شود. خواندن دوبارهٔ bytes مبدأ پس از snapshot، تغییر هم‌زمان را رد می‌کند. با این حال توقف نویسندگانِ خارج از قرارداد قفل لازم است. انتشار آرشیو با نوشتن کامل، fsync و ایجاد اتمی فایل جدید انجام می‌شود؛ بازاجرا فایل قبلی را جایگزین نمی‌کند. خود JSON آرشیو snapshot منطقیِ ردیف‌ها و چکیدهٔ فایل‌های منبع را نگه می‌دارد؛ فایل خام SQLite نیست و ابزار restore اجرایی ندارد.

**۳۸ آزمون تازه، صفر شکست و صفر صرف‌نظر** ثبت شد. شمارش و خروجی نهایی در `integration/history-recovery-v01/` ثبت شده است. کارزار ۲۸۹آزمونی قبلی در این کار محلی تکرار نشده؛ نتیجهٔ قدیمی همچنان فقط به head قبلی تعلق دارد. workflow موجود یک مرحلهٔ اختصاصی `history-test` دارد؛ سایر آزمون‌های خودکار مخزن، سیاست پیشین CI هستند.
