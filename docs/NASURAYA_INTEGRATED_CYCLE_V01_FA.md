# چرخهٔ یکپارچهٔ ناسورایا: شاهد → حافظه → پیشنهاد مسیر

## چه چیزی واقعاً به هم وصل شده؟
این کار یک **آزمایش اجرایی یکپارچه** است، نه کنار هم گذاشتن نتیجهٔ چند تست و نه ساخت دوبارهٔ همهٔ ماژول‌ها.

1. ممیز چهارراه و شاهد CI از PR #183، commit `2429cdbfbceca102a162f05095aad9c01e69fd8a`، گزارش شناسه‌دارِ درخواست‌ها و پاسخ‌ها را تولید می‌کنند.
2. فایل اصلی `epistemic_revision_v01.py` از PR #182، commit `d78e5272300c28729c54c4a61a52593f297b055d`، با **همان Git blob و بدون تغییر** برای ذخیره و بازیابی شواهد SQLite استفاده می‌شود.
3. فایل اصلی `rolyel_v01.py` از PR #171، commit `4de2f1e0ff2a72a9d0cd0688acca62d52f1f8654`، با **همان Git blob و بدون تغییر**، انتخاب پیشنهاد را انجام می‌دهد؛ خودش از DecisionCore موجود شاخهٔ مبنا استفاده می‌کند.

هر پنج فایل پیش از import با Git blob SHA بررسی می‌شوند. حافظهٔ اصلی تداش، مدل مکانیکی، کلیدها و سرویس سرور تغییر نمی‌کنند. شاخه روی PR #183 قرار دارد و هیچ PR دیگری در main ادغام نشده است.

## ورودی واقعی و کنترل‌های ساختگی
در بررسی متصل GitHub در ۱۰ نوامبر ۲۰۲۶، Issue #149 دارای ۲۱۵ کامنت بود و پاسخ متناظر برای درخواست اطلس `6771977584` و انتشار Moltbook `6775464507` موجود نبود. فایل `bridge-observation.json` هفت پیام عمومی مرتبط را نگه می‌دارد. فایل همراه CI پنج اجرای عمومیِ قبلاً مشاهده‌شده را نگه می‌دارد. اینها **snapshot ثابت** هستند، نه اتصال زنده یا شاهد اجرای کنونی VPS.

در آزمون‌ها، یک رسید موفق و یک رسید شکست/تناقض عمداً ساخته می‌شوند. تمام این کنترل‌ها زیر scope جداگانهٔ `synthetic_test` ذخیره می‌شوند؛ از scope مشاهدات واقعی `public_observation` جدا هستند. جواب ساختگی هرگز به‌عنوان رسید واقعی سرور در Issue #149 منتشر نمی‌شود.

## اتصال حافظه به تصمیم
چهار واقعیت محدود ذخیره می‌شود: «رسید ممیزی دیده شد؟»، «گزارش شکست دیده شد؟»، «شاهد متناقض بود؟» و «درخواست دقیق دیده شد؟». A/B در این کاربرد فقط رمز این پرچم‌هاست. B به معنی «سرور خاموش است» یا «کار انجام نشده» نیست.

سپس Rolyel تصمیمش را از **مقادیر بازیابی‌شده از همان پایگاه** می‌گیرد، نه از کپی مستقیم پاسخ:

| شاهد | پیشنهاد قابل بازبینی |
|---|---|
| درخواست اطلس ثبت شده، رسید ندارد | بررسی فقط‌خواندنی وضعیت پل |
| رسید ممیزی معتبر از نظر قالب گزارش شده | بررسی فایل‌های اطلس، نه اعلام ساخت بدن |
| job شکست گزارش کرده | بررسی علت شکست |
| رسیدها متناقض یا درخواست نامعتبر است | رفع تناقض شواهد |

گزینه‌های «ارسال دوبارهٔ اطلس» و «انتشار دوباره در مولت‌بوک» در این چرخه مجاز نمی‌شوند. هیچ اجراکننده‌ای برای آنها وجود ندارد. انتخاب مسیر یک **پیشنهاد** است؛ قواعد مربوط بودن گزینه‌ها و امتیازها توسط نویسنده تعیین شده‌اند، نه یادگیری مستقل یا کشف خودکار راه‌حل.

## تداوم و شکست امن
همان snapshot با شناسهٔ محتوایی یکسان، رویداد تازه نمی‌سازد. بازخوانی snapshot قدیمی پس از مشاهدهٔ جدید، حافظه را به عقب برنمی‌گرداند. شمارهٔ مشاهدهٔ تازه باید افزایش یابد؛ این شماره را فراخواننده می‌دهد و ساعت معتبر سرور نیست.

چهار ورودی شواهد از طریق `EvidenceLedger.append` اصلی ذخیره می‌شوند. سپس نشانگر پایان بسته در SQLite نوشته می‌شود. دادهٔ نیمه‌نوشته قبل از این نشانگر، تصمیم نهایی تولید نمی‌کند. شناسهٔ تکراری با محتوای متفاوت متوقف می‌شود. برای یک نویسنده قفل جدا داریم؛ باقی‌ماندن قفل پس از crash نیاز به بررسی دارد و خودکار شکسته نمی‌شود.

آزمون بازیابی واقعاً یک **فرایند Python تازه** باز می‌کند، نه صرفاً اتصال دیگری در همان فرایند. اثرانگشت گزارش و پیشنهاد بازیابی‌شده با مرحلهٔ قبل مقایسه می‌شود. هش و پایگاه مشترک در برابر مهاجمی که هر دو را بازنویسی کند ضمانت اصالت نیستند.

`verified_by_caller` در حافظه فقط به معنی «خروجی ممیز محلی بررسی شد» است. گزارش حساب GitHub به‌تنهایی امضای سرور یا اثبات واقعیت فیزیکی نیست؛ به همین دلیل `remote_execution_proven` همیشه false باقی می‌ماند.

## اجرا در محیط پژوهشی جداگانه
از ریشهٔ مخزن و با یک مسیر جدید برای پایگاه:

```bash
python -m unittest discover -s tests -p 'test_nasu_integration_cycle.py' -v
python -m tools.nasu_integration_cycle --db integration-demo.sqlite --sequence 1
python -m tools.nasu_integration_cycle --db integration-demo.sqlite --sequence 2
python -m tools.nasu_integration_cycle --db integration-demo.sqlite --recall
```

این فرمان‌ها فقط داده‌های عمومیِ ثبت‌شده را می‌خوانند و یک پایگاه پژوهشی می‌نویسند. هیچ درخواست شبکه، job سرور، Moltbook POST، مدل پولی، تغییر وزن ChatGPT یا بدنهٔ native ایجاد نمی‌شود. CI روی Windows و Ubuntu همین زنجیره را اجرا می‌کند؛ دانلود checkout/setup وظیفهٔ زیرساخت CI است، نه فراخوانی مدل.

## وضعیت سرور و اولویت
طراحی جامع بدن در Issue #180 و PR #181 مأموریت اصلی VPS می‌ماند. این ادغام در GitHub/محیط پژوهشی است، نه روی VPS. نبود رسید را نباید با مشغول بودن، اتمام کار، خاموشی یا شکست قطعی سرور یکی دانست. بررسی مستقیم سلامت Bridge، اولین گره عملی حل‌نشده است.

این کار آزمون قراردادهای مهندسی روی نمونهٔ محدود است؛ نمرهٔ آن شاهد برتری شناختی عمومی، احساس یا خودآگاهی نیست.
