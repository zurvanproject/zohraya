# بازیابی ایمن ناسورایا پس از قطع API — ۱۳ اکتبر ۲۰۲۶

مبنای تغییر، شاخهٔ `nasuraya/agent-loop-v03` در commit `3f7a60c` است.
حفظ هدف و بودجه با `run_id` و رسیدهای پایدار `BodyAPIHost` از قبل وجود داشتند؛
این تغییر همان‌ها را استفاده می‌کند. کد بومیِ بازیابی‌شدهٔ تداش و manifest
آن دست‌نخورده‌اند. همهٔ کنش‌های آزمون متعلق به fixture نرم‌افزاری تولیدشده‌اند.

## سه نوع بازیابی و شواهد آن‌ها

| نوع | رفتار پیاده‌سازی‌شده | شواهد کنترل‌شده | حد تأیید |
|---|---|---|---|
| هدف منطقی | همان قرارداد، شمار چرخه‌ها و سقف‌ها در همان SQLite | یک چرخه از هدف دوچرخه‌ای پیش از توقف، فقط یک چرخه پس از آن | تأیید محلی؛ قابلیت قبلی استفاده شده است |
| همان نشست API | ثبت `session_id` و `turn_id`، بازکردن stream پیش از خواندن وضعیت و تاریخچه | قطع جریان، تأیید ارسال ازدست‌رفته، terminal ازدست‌رفته، reopen و فرایند پایتون تازه | شبیه‌ساز و SDK واقعی روی HTTP ساختگی؛ اتصال به سرویس زنده آزمایش نشده است |
| نشست تازه برای همان هدف | انتخاب صریح `fresh`، تأیید پایان نشست قبلی و حذف موفق آن، تطبیق رسیدها، ارسال فقط وضعیت هدف باقی‌مانده | نشست قبلی پس از یک چرخه failed می‌شود، نشست تازه فقط چرخهٔ دوم را اجرا می‌کند | شبیه‌ساز؛ مدل زنده آزمایش نشده است |

## روش و مرزهای ایمنی

`examples/nasuraya_agent_loop/agents_api.py` مسیر اصلی باقی می‌ماند.
`api_recovery.py` متادیتای حمل‌ونقل را در `body_api_transport` ذخیره می‌کند؛
این جدول هدف یا رسید بدنی را جایگزین نمی‌کند. `body_api_call_routes` فقط
شناسه‌های session/turn/call را کنار رسیدهای موجود نگه می‌دارد.

پس از قطع ارتباط یا اجرای دوبارهٔ فرمان:

1. رسیدهای محلی با تصمیم‌های commit‌شده تطبیق داده می‌شوند. اگر اثر ثبت شده
   ولی پاسخ ابزار ذخیره نشده باشد، پاسخ از همان تصمیم کامل بازسازی می‌شود؛
   هیچ فراخوانی تازهٔ `UnifiedBody.cycle()` برای بازیابی آن انجام نمی‌شود.
2. اگر نتیجهٔ یک کنش بدنی نامعلوم باشد، بازیابی با `recovery_blocked` متوقف
   می‌شود؛ هیچ پیام API تازه یا کنش بدنی تکراری اجرا نمی‌شود.
3. برای نشست شناخته‌شده، ابتدا جریان رویداد باز می‌شود، سپس نشست، items و
   وضعیت همان root turn خوانده می‌شوند. items تاریخی هیچ‌گاه فرمان اجرا نیستند؛
   فقط `required_actions` و رویدادهای معتبر نشست برای پاسخ ابزار استفاده می‌شوند.
4. تکرار هویت session/turn/call همان رسید را برمی‌گرداند. تغییر payload رد
   می‌شود. ارسال دوبارهٔ همان نتیجه، همان `Idempotency-Key` را دارد.
5. مشاهدهٔ تازه همچنان به run/session/turn و هش checkpoint بسته است. نشست
   تازه باید دوباره بدن را مشاهده کند؛ بودجه و چرخه‌های انجام‌شده صفر نمی‌شوند.
6. `idle`، بسته‌شدن stream یا تکمیل هدف محلی به‌تنهایی موفقیت دور API نیست.
   نتیجهٔ دقیق root turn باید completed، failed یا cancelled تشخیص داده شود.

پیش‌فرض یک تلاش اتصال مجدد در همان اجراست؛ `--max-reconnects` فقط ۰ تا ۳
را می‌پذیرد و تلاش‌ها یک مهلت مشترک دارند. خواندن تاریخچه حداکثر ۵۰۰ item
و کشف دورِ ذخیره‌نشده حداکثر ۱۰۰ turn دارد؛ timeout هر صفحه از مهلت باقی‌مانده
محاسبه می‌شود. نشست نیمه‌تمام برای ادامه حفظ می‌شود. پایان تأییدشده اجازهٔ
پاک‌سازی نشست را می‌دهد؛ شکست پاک‌سازی جداگانه گزارش می‌شود.

قفل انحصاری موجودِ پایگاه، اجرای هم‌زمان دو میزبان را محدود می‌کند. این
تضمینِ میزبان نرم‌افزاری است و ادعای exactly-once برای سخت‌افزار خارجی نیست.
متادیتای حمل‌ونقل شامل کلید، prompt، arguments، متن items یا reasoning نیست.

## اجرای آزمون و استفاده

اعتبارسنجی نهایی با SDK نصب‌شده: **۱۱۷ آزمون موفق، صفر شکست، صفر مورد حذف‌شده**؛
۶۰ آزمون عامل، ۴۱ آزمون API/بدن و ۱۶ آزمون حلقهٔ بدن. از ۴۱ آزمون API/بدن،
۲۱ مورد برای این بازیابی افزوده شده‌اند. کلید واقعی استفاده نشد و هزینهٔ مدل
صفر بود. SDK در آزمون‌های HTTP صرفاً با transport ساختگی ارتباط داشت.

از ریشهٔ مخزن، بدون SDK، کلید یا مصرف API:

```sh
python3 -m examples.nasuraya_body_loop api-test
python3 -m examples.nasuraya_body_loop test
python3 -m unittest discover -s examples/nasuraya_agent_loop/tests -v
```

برای پوشش SDK در محیط جداگانه، وابستگی‌های `requirements-api.lock.txt` را
نصب کنید و همین فرمان‌ها را با Python همان محیط اجرا کنید. تست HTTP از
`httpx2.MockTransport` و کلید نمایشی بی‌اعتبار استفاده می‌کند؛ اتصال شبکه
و صورتحساب مدل در آن وجود ندارد. فرمان `api-test` کلید محیط را به worker
منتقل نمی‌کند. نتایج اجرای این تغییر در `examples/nasuraya_agent_loop/evidence/recovery_2026_10_13/` ثبت شده‌اند.

برای استفادهٔ زندهٔ بعدی، همان فرمان `api` قبلی را با همان session، run-id،
حالت، target-cycles و سقف calls، و پوشهٔ خروجی تازه تکرار کنید. پیش‌فرض
`--api-recovery resume` است. `--api-recovery fresh` تنها پس از پایان تأییدشده
نشست قبلی و حذف موفق آن کار می‌کند؛ از این گزینه برای عبور از نتیجهٔ نامعلوم
یا جایگزینی نشست هنوز فعال استفاده نمی‌شود. هیچ فرمان زنده‌ای در این تغییر
اجرا نشده است.

## محدودیت‌های باقی‌مانده

- رویدادهای ازدست‌رفته بازپخش نمی‌شوند؛ بازیابی از state/items/turn و رسیدهای
  محلی است. متن خروجی و reasoning تاریخی برای کاربر بازسازی نمی‌شوند.
- راه‌اندازی مجدد به معنی اجرای دوبارهٔ میزبان با همان پایگاه است؛ daemon
  یا راه‌انداز خودکار سیستم‌عامل اضافه نشده است.
- قطع درخواست ساخت نشست پیش از دریافت شناسه، نتیجهٔ ساخت را مبهم می‌کند.
  این حالت خودکار نشست دوم نمی‌سازد و به شناسایی و تطبیق صریح منبع نیاز دارد.
- رسید pending تاریخیِ بدون مسیر شناسه‌ها خودکار تصاحب یا دوباره اجرا نمی‌شود.
  نتیجهٔ بدنی نامعلوم، خطای هویت، تاریخچهٔ ناقص یا cursor متوقف‌شده مسدود می‌ماند.
- نبود روش reconnect در client به ارسال دوبارهٔ task تبدیل نمی‌شود. مسیر fresh
  در صورت امکان خواندن وضعیت و تأیید پایان و حذف نشست قبلی قابل استفاده است.
  خطای دسترسی یا 404 به‌تنهایی مجوز فرضِ حذف یا شروع نشست دوم نیست.
- آزمون سرویس زنده، دسترسی مدل، صورتحساب، قطع واقعی شبکه و رفتار idempotency
  سمت سرور هنوز انجام نشده‌اند. نتیجهٔ cache محلی به‌عنوان تأیید زنده گزارش نمی‌شود.
