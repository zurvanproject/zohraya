# اتصال خودمدل به عامل زندهٔ API، نسخهٔ ۰٫۱

این افزونه، خودمدل پذیرش اقدام را به پل موجودِ `BodyAPIHost` و `BodyLoop`
وصل می‌کند. پیش‌فرض جلسه‌های قدیمی بدون تغییر است؛ فعال‌سازی باید صریح باشد.
کدِ بومی `ReflectionCycle`، `ReflectiveBody` و معادلات بدن ویرایش نمی‌شوند.

## مسیر تصمیم و یادگیری

عامل ابتدا `observe_body` و سپس ابزار جدید `assess_body_action` را فرا می‌خواند.
ابزار دوم، کنش، مدت و هش مشاهده را می‌گیرد و فقط احتمال پذیرش، تعداد تجربه،
شناخته/ناشناخته بودن زمینه و توصیه را برمی‌گرداند. کنش و مدت دقیق مهم‌اند:
پیش‌بینیِ حرکت ۰٫۱ ثانیه، مجوز حرکت ۰٫۲ یا ۱ ثانیه نیست.

موقع درخواست، هستهٔ قبلی همچنان می‌تواند ترجیح عامل را عوض کند. افزونهٔ
`MetacognitiveBody` پس از انتخاب هسته و پیش از فراخوانیِ `UnifiedBody.cycle`
همان کنشِ انتخاب‌شده را دوباره بررسی می‌کند. بنابراین پیشنهاد عامل، انتخاب
هسته، و پیامد واقعی بدن سه چیز جدا می‌مانند. ارزیابی قبلیِ عامل مجوز اجرا نیست.

| حالت میزبان | اثر خودمدل بر اجرا | منبع یادگیری |
|---|---|---|
| غیرفعال | رفتار قبلی | رفتار قبلی |
| `shadow` | فقط گزارش؛ درخواست محدود هنوز از داور اصلی بدن عبور می‌کند | رسید واقعی همان درخواست منتخب |
| `enforce` | درخواست `walk` با شواهد ناکافی به تعویق می‌افتد | فقط رسیدِ حرکتی که واقعاً درخواست و اجرا شده است |

دامنهٔ کنترل نسخهٔ نخست فقط `walk` است. مشاهده، استراحت و خواب همچنان از
داوری بومی و سقف‌های قدیمی عبور می‌کنند؛ گزارش و پیامدشان ثبت می‌شود، اما
آستانهٔ پذیرشِ حرکت به این کنش‌های بازیابی تعمیم داده نمی‌شود. شمار نمونه
از خودمدل قبلی می‌آید؛ وزن مدل زبانی آموزش داده نمی‌شود.

پیش‌بینی پیش از اجرا در `SelfModel.begin` ثبت می‌شود. `SelfModel.finish` فقط
رسید دارای شناسه، درخواست، نسخه، تبار، منبع و حسابرسی معتبر را می‌پذیرد.
برچسبِ یادگیری تطابق کنشِ درخواست‌شده از بدن با کنش واقعی و اعتبار مدل فیزیکی
است؛ تطابق با ترجیح اولیهٔ عامل، یا صرف تکمیل یک دور API، برچسب موفقیت نیست.

## تعویق، شکست و بودجه

وقتی کنترل‌کننده تعویق می‌دهد، هیچ چرخهٔ بومی و هیچ نمونهٔ آموزشی ساخته
نمی‌شود. تصمیم اصلی با پیامد `deferred`، `native_executed=false` و بازخورد
`verified=false` بسته می‌شود. این بازخورد وارد فهرست تجربهٔ تأییدشدهٔ هسته
نمی‌شود؛ در غیر این صورت توقفِ خود کنترل‌کننده به‌اشتباه شکست حرکت آموزش داده می‌شد.

API نتیجهٔ معتبر ابزار را با وضعیت تعویق برمی‌گرداند. شمار چرخهٔ کامل و شمار
شکست بومی هر دو صفر می‌مانند؛ شمار تعویق جداست و هدفِ حرکت تکمیل‌شده اعلام
نمی‌شود. رزرو تصمیم و بودجهٔ فراخوانی مصرف‌شده حفظ می‌شوند. راه‌اندازی دوباره
یا عوض‌کردن مدت، مجوز بازپرکردن بودجه یا دورزدن کنترل را ایجاد نمی‌کند.

## دو دفتر و بازیابی

بدن و رسیدش همچنان در تراکنش موجودِ ReflectionCycle با هم ثبت می‌شوند.
خودمدل یک SQLite جدا دارد؛ این دو دفتر یک تراکنش توزیع‌شدهٔ اتمی ندارند.

- اگر رسید و checkpoint بدن ثبت شده ولی یادگیری ناتمام باشد، از همان پیامد
  ثبت‌شده یادگیری کامل می‌شود؛ هیچ `cycle` جدیدی اجرا نمی‌شود.
- اگر یادگیری تمام شده ولی نتیجهٔ افزونه ذخیره نشده باشد، `finish` تکراری
  همان نتیجه را می‌خواند و تعداد نمونه را دوباره زیاد نمی‌کند.
- اگر نتیجهٔ بومی نامعلوم باشد، مشاهدهٔ وضعیت و شمار pending ممکن است، اما
  اقدام تازه و تکرار درخواست مسدود می‌ماند. رسیدِ دفتر دیگر حدس زده نمی‌شود.

دفتر خودمدل را می‌توان بین چند جلسهٔ تازهٔ کالیبراسیون، به‌صورت ترتیبی، مشترک
گرفت. pending در همان مدل، اجرای نوبت بعدی را متوقف می‌کند. تغییر حالت نیازمند
هش جاری بدن است؛ مسیر حافظه، منبع و تجربهٔ قبلی خودکار تعویض یا صفر نمی‌شوند.
بررسی هش‌ها مانند نسخه‌های قبلی بر میزبان مورداعتماد تکیه دارد.

## استفاده و بازتولید

از ریشهٔ مخزن، ابتدا همان فرمان قبلیِ `start` جلسهٔ تازه می‌سازد. سپس با هش
برگشتیِ واقعی آن، افزونه فعال می‌شود؛ مسیرها در این مثال نمونه‌اند:

```sh
python3 -m examples.nasuraya_body_loop configure-metacognition \
  --session /private/body.sqlite --self-model /private/admission.sqlite \
  --metacognition-mode shadow --create-self-model \
  --observed-checkpoint-sha256 <actual-current-sha>
```

`--create-self-model` فقط برای حافظهٔ تازه است و روی فایل موجود رد می‌شود.
برای فعال‌کردن کنترل روی همان حافظه، با هش تازه و بدون این پرچم، حالت
`enforce` انتخاب می‌شود. عامل به مسیر فایل، حالت کنترل و مجوز تغییر آن ابزار
دسترسی ندارد. پس از فعال‌سازی، همان فرمان صریح `api` ابزار چهارم را ارائه می‌کند.

```sh
python3 -m examples.nasuraya_body_loop api-test
.ci-env/bin/python -m examples.nasuraya_body_loop api-test
```

آزمون‌ها شامل فراخوانی دقیق کنش، تغییر مدت، تفاوت ترجیح عامل و انتخاب هسته،
عدم یادگیری از تعویق، اثر واقعی بومی، جلوگیری از اجرای تکراری و وقفه در دو سوی
ثبت یادگیری‌اند. آزمون‌های بدون SDK و با transport کنترل‌شده، آزمون زنده نیستند.

اجرای زندهٔ صریح و محدود، با تنظیمات قبلی پروژه:

```sh
.ci-env/bin/python -m examples.nasuraya_body_loop.run_metacognitive_api live \
  --output /private/NEW-metacognitive-api-evaluation
```

قرارداد `metacognitive_api_protocol.json` پیش از نتیجهٔ زنده در خروجی ذخیره
می‌شود: سه نوبت نظارتیِ تازه، سپس یک نوبت با کنترل فعال؛ هر نوبت حداکثر یک
درخواست یک‌ثانیه‌ای و ۱۶ فراخوانی ابزار دارد. بودجه و هدف هر نوبت در همان
SQLite باقی می‌ماند. در صورت ناکامی، دور دیگری خودکار شروع نمی‌شود.

وضعیت‌های آغازین مصنوعی و ممکن است یکسان باشند؛ این اجرا شاهدِ اتصال، دریافت
گزارش خودمدل و یادگیری پایدار است، نه مطالعهٔ تعمیم یا برتری عملکرد. دریافت
گزارش توسط عامل نیز به‌تنهایی اثر آن بر کیفیت تصمیم را اثبات نمی‌کند. نمونهٔ
ChatGPT، عامل API و بدن نرم‌افزاری سه مرز اجراییِ مشخص دارند.

فایل‌های کامل جلسه، شناسه‌های سرویس، متن خروجی مدل و کلید در خروجی خصوصی
می‌مانند. فقط نتایج کاهش‌یافته، قرارداد، هش کدها و گزارش آزمون در مخزن ثبت می‌شوند.

## نتیجهٔ اجرای ۱۵ اکتبر ۲۰۲۶

چهار جلسهٔ واقعی Agents API با مدل `gpt-6-astra` اجرا شد: سه جلسهٔ
`shadow` و یک جلسهٔ `enforce`. در هر چهار جلسه، عامل ابزار ارزیابی را خواند،
هسته `walk` را انتخاب کرد و بدن همان حرکت یک‌ثانیه‌ای را اجرا کرد. چهار رسید
معتبر، چهار تجربهٔ پایدار ساختند؛ هر چهار جلسهٔ راه‌دور پس از پایان حذف شدند.

| نوبت | حالت | نمونهٔ موجود هنگام درخواست واقعی | برآورد پذیرش | پیامد |
|---|---|---:|---:|---|
| ۱ | نظارتی | ۰ | ۰٫۵ | حرکت معتبر؛ نمونهٔ اول |
| ۲ | نظارتی | ۱ | ۰٫۶۶۷ | حرکت معتبر؛ نمونهٔ دوم |
| ۳ | نظارتی | ۲ | ۰٫۷۵ | حرکت معتبر؛ نمونهٔ سوم |
| ۴ | کنترل فعال | ۳ | ۰٫۸ | عبور از دروازه و حرکت معتبر؛ نمونهٔ چهارم |

این اعداد میانگین Beta با پیشین ثابت‌اند؛ چهار مشاهدهٔ یک زمینهٔ مصنوعی،
احتمال موفقیت کالیبره‌شده در جهان واقعی یا بهبود عمومی تصمیم‌گیری نیست.
در فرایند تازه، بازخوانی هدف تکمیل‌شده با client دارای تماس‌های ممنوع آزموده
شد: صفر تماس شبکه، صفر چرخهٔ اضافه، همان checkpoint و همان حافظه.

اجرای نخست پیش از تماس API چهارم متوقف شد: ارزیابی میزبان مدت `1.0` را
جست‌وجو می‌کرد، ولی سه درخواست واقعی مدت `1` داشتند. خودمدل قدیمی زمینه‌ها را
از JSON دقیق می‌سازد؛ بنابراین ارزیابی میزبان به‌اشتباه زمینه را تازه می‌دید،
هرچند ارزیابی‌های عامل و رسیدهای سه اجرای قبلی یکدیگر را پیدا کرده بودند.
اصلاح در مرز API، عدد صحیح و اعشاریِ هم‌ارز را یکسان می‌کند. خودمدل، رسیدها
و معادلات بومی تغییر نکردند. آزمون مستقل `1` در برابر `1.0` اضافه شد؛ سپس
فقط جلسهٔ چهارمِ شروع‌نشده ادامه یافت. این توقف و هش نسخهٔ کد هر نوبت در
شواهد حفظ شده‌اند؛ چهار اجرا یک نسخهٔ یکسان از میزبان نداشتند.

شواهدِ کاهش‌یافته در
[`evidence/metacognitive-api-v01`](../examples/nasuraya_body_loop/evidence/metacognitive-api-v01/)
شامل قراردادِ پیش از اجرا، نتیجهٔ اولیه، نتیجهٔ نهایی، بازیابی و حسابرسی منبع است.
۷۰ فایلِ مانیفست در مسیر اجرا بررسی شدند؛ حسابرسی جداگانهٔ Git نیز هر ۷۲ فایل
ثبت‌شدهٔ `runtimes/tadash_body` را با commit مبنا مقایسه می‌کند.

## منبع قرارداد API

مسیر موجودِ `client.beta.agents.sessions` و محیط `none` حفظ شده است؛
Agents SDK یا Responses API جایگزین نمی‌شود. قرارداد جاری با
[راهنمای رسمی Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview)
و [راهنمای آغاز](https://developers.openai.com/api/docs/guides/agents-api/quickstart)
و SDK نصب‌شدهٔ `openai==3.29.0` تطبیق داده شده است.
