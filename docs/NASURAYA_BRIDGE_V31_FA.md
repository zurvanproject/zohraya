# Nasuraya Linux Bridge v3.1 | ارتقای کنترل‌شدهٔ مأموریت‌های پژوهشی

**وضعیت کد:** نامزد بازبینی، بدون استقرار خودکار. GitHub Issue به خودی خود فرمان نیست. این بسته برای ادغام خودکار در `main` طراحی نشده است.

## هدف و قرارداد

- بر اساس بریج زندهٔ Ubuntu با SHA-256 مشاهده‌شدهٔ `a8fdac423d1161bf4209e43f991168df31721cb1529e367d01e2b5c10841dd74`، نه نسخهٔ قدیمی main.
- ۲۰ handler قدیمی + `help` باید دست‌نخورده بمانند. دستورهای جدید دقیقاً `research-start`, `research-status`, `research-stop` هستند.
- پیام GitHub فقط وقتی فرمان محسوب شود که **خط اول** دقیقاً با دستور مجاز مطابقت داشته باشد. سطرهای توضیحی بعدی مجازند ولی هیچ دستوری از داخل آن‌ها استخراج نمی‌شود.
- GitHub Bridge به shell، arbitrary prompt، مدل یا URL دلخواه تبدیل نمی‌شود؛ متون Issue و خروجی مدل هرگز به صورت دستور اجرایی اجرا نمی‌شوند.

## آزمایش محدود پژوهش

`research-start` تنها یک batch ثابت و مصنوعی ۱۶ فراخوانی Ollama محلی با مدل `qwen3:4b-instruct` را برای مأموریت پژوهشی #290 آغاز می‌کند: چهار مسئله × چهار حالت `M0P0`, `M1P0`, `M0P1`, `M1P1`. ورودی از متن آزاد Issue خوانده نمی‌شود؛ داده و کلید پاسخ معیار در خود برنامه ثابت‌اند و کلید به prompt وارد نمی‌شود. این **آزمایش ۳۲۰تایی کامل** نیست و عملکرد یا تغییر وزن مدل را اثبات نمی‌کند.

- حداکثر ۱۶ درخواست، ۹۵ ثانیه برای هر درخواست، ۱۶۰۰ ثانیه محدودیت نرمِ batch، ۱۰۰۰ توکن خروجی و ۴۰۹۶ توکن context.
- پرونده‌های محلی در `/var/lib/nasuraya/bridge-research-v1` از دفترهای اصلی مستقل‌اند. پاسخ خام هرگز در کامنت GitHub قرار نمی‌گیرد.
- `research-status` فقط آمار و hash و وضعیت را گزارش می‌کند؛ `research-stop` علامت توقف می‌سازد که بین درخواست‌ها بررسی می‌شود. توقف درخواست در حال اجرای Ollama را قطع فوری نمی‌کند.
- کار پژوهشی خودکار با نصب آغاز نمی‌شود. اجرای موفق واحد/fixture به معنی تأیید کیفی Qwen نیست.

## تغییر واقعی و کنترل امنیتی

۱. فقط شرط استخراج دستور در `poll()` به بررسی خط اول تغییر می‌کند.
۲. فهرست فرمان‌ها سه عضو اضافه می‌گیرد و تنها سه handler ثابت افزوده می‌شود.
۳. یک فایل مستقل `nasu_bridge_research.py` در `/usr/local/lib/nasuraya/` قرار می‌گیرد.
۴. فقط سرویس `nasuraya-bridge.service` یک بار restart می‌شود، پس از پشتیبان‌گیری. فایل‌های SQLite، حافظهٔ اصلی، مدل‌ها، زمان‌بندها و سورس `main` تغییر نمی‌کنند.

## مسیر اجرا، فقط پس از بازبینی تفاوت واقعی

فایل‌های زیر باید از **یک commit ثابت و تأییدشده** دریافت شوند:

- `tools/nasu_bridge_research.py`
- `tools/preview_nasuraya_bridge_v31.py`
- `tools/install_nasuraya_bridge_v31.py`

در پوشهٔ واحد روی Ubuntu، نخست این دستور فقط‌خواندنی اجرا شود:

```sh
python3 install_nasuraya_bridge_v31.py --preview
```

این دستور SHA-256 و diff دقیق فایل نصب‌شده را نشان می‌دهد و **هیچ چیز نمی‌نویسد**. اگر SHA یا ساختار بریج، allowlist، فایل جدید یا هش اسکریپت‌ها متفاوت باشند، متوقف می‌شود.

**تنها پس از مشاهدهٔ کامل diff و تأیید آن**، فرمان نصب با SHA دقیق منتشرشده از preview قابل اجراست:

```sh
sudo python3 install_nasuraya_bridge_v31.py --apply --approve-sha <SHA256_OF_PROPOSED_BRIDGE>
```

نصب‌کنندهٔ root-only، ابتدا نسخهٔ اصلی را در `/var/backups/nasuraya-bridge-v31` نگه می‌دارد، دو فایل را با write اتمیک می‌گذارد و **فقط** Bridge را restart می‌کند. در صورت شکست restart یا عدم تطبیق SHA پس از نصب، rollback به نسخهٔ پیشین را امتحان می‌کند. این یک مکانیزم rollback آزمایشی است، نه ضمانت صددرصدی بازیابی در هر شکست میزبان.

## آزمون‌ها و محدودیت‌های صحت

```sh
python3 -B -m unittest discover -s tests -p 'test_*bridge_v31.py' -v
```

در محیط ایزوله، آزمون‌های تغییر allowlist، منع فرمان میانی، حفظ handlerهای قدیمی، حالت‌های مدل مصنوعی، idempotence، توقف cooperative، جلوگیری از اجرای مجدد، اعمال نصب مصنوعی و rollback خطای service اجرا می‌شوند. آزمون‌های service با mock هستند؛ **نصب واقعی روی VPS هنوز جداگانه باید تأیید شود**.

### متوقف‌کننده‌ها

- فایل زندهٔ Bridge یا SHA با نسخهٔ تأییدشده تفاوت داشته باشد.
- دسترسی GitHub خاموش، پاسخ با تأخیر یا request قدیمی تکرار شود.
- سرویس Bridge فعال نباشد، پیش از نصب runner جدیدی موجود باشد، یا مالک دسترسی/هزینهٔ جدید را تأیید نکرده باشد.
- پس از نصب: `agent-status`, `research-status` و یک پژوهش محدود به‌عنوان سه مشاهدهٔ مستقل لازم‌اند. ادعای «دسترسی عمومی به سرور از GitHub» یا «خودتوسعه‌دهی نامحدود» از این تغییر نتیجه نمی‌شود.
