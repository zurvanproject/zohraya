# حلقهٔ محلی ناسورایا با بدن نرم‌افزاری تداش

این مسیر، DecisionCore v0.1 و ReflectionCycle v0.2 بازیابی‌شده را به چرخهٔ واقعی
`UnifiedBody.cycle()` متصل می‌کند. چرخهٔ مشاهده ← تصمیم ← اجرا ← ارزیابی در یک
بدن نرم‌افزاری با وضعیت آغازینِ ساخته‌شده برای آزمون اجرا می‌شود. API فراخوانی
نمی‌شود. مدل زبانی و بدن فیزیکی در این مسیر اجرا نمی‌شوند.

Python 3.11 یا بالاتر و Linux با کتابخانهٔ استاندارد کافی است. از ریشهٔ مخزن:

```bash
python3 -m examples.nasuraya_body_loop test
python3 -m examples.nasuraya_body_loop demo --fixture sleep --steps 3 --max-actions 12 --output-dir /tmp/nasuraya-body-demo
```

خروجی باید تازه باشد. سه فایل متنی و یک checkpoint در SQLite نوشته می‌شوند:
`summary.json`، `events.jsonl`، `decisions.json` و `session.sqlite`.

اجرای مرحله‌ای، هر فرمان در یک فرایند تازه:

```bash
python3 -m examples.nasuraya_body_loop start --fixture sleep --max-actions 12 --session /tmp/nasuraya-body.sqlite
python3 -m examples.nasuraya_body_loop observe --session /tmp/nasuraya-body.sqlite
python3 -m examples.nasuraya_body_loop step --decision-id step-1 --session /tmp/nasuraya-body.sqlite
python3 -m examples.nasuraya_body_loop status --session /tmp/nasuraya-body.sqlite
```

پیش از هر کنش تازه، دوباره `observe` لازم است. وضعیت و سقف کنش در SQLite حفظ
می‌شوند؛ بستن برنامه بودجه را صفر نمی‌کند. تکرار یک شناسهٔ تکمیل‌شده رسید قبلی
را برمی‌گرداند. تغییر مدت آن درخواست رد می‌شود. عملیات `running` حل‌نشده مانع
کار تازه است و به بررسی و تطبیق صریح پیامد نیاز دارد؛ خودکار دوباره اجرا نمی‌شود.
قفل فایل، نویسندهٔ هم‌زمان را رد می‌کند. شروع دوباره روی فایل موجود ممنوع است. دفترِ غیرمرتبط پیش از هر مهاجرت، فقط‌خواندنی بررسی و رد می‌شود.
حالت `--mode observe` هیچ کنش تغییردهنده‌ای اجرا نمی‌کند.

## مدل وضعیت و بازخورد

مشاهده از checkpoint معتبر خود کد بدن می‌آید: شمارهٔ نسخه، وضعیت کمینهٔ بدن،
جایگاه و حالت بدنی، و خلاصهٔ درون‌حسیِ شبیه‌سازی. این اطلاعات گزارشِ وضعیت کد
هستند و احساس یا فیزیولوژی انسان را اندازه نمی‌گیرند.

امتیازهای دو گزینهٔ «راه‌رفتن» و «مشاهده»، فرض‌های صریحِ مهندسیِ fixture هستند.
نتیجهٔ موردانتظار، قراردادِ نام اقدام است؛ پیش‌بینی احتمالاتی کالیبره‌شده نیست.
خود بدن می‌تواند اقدام درخواست‌شده را وتو کند. بازخورد همان پیامد واقعیِ برگشتی
در دفتر ذخیره می‌شود و ReflectionCycle با قرارداد و زمینهٔ یکسان آن را بازیابی
می‌کند. شمارهٔ نسخهٔ مشاهده در شاهدِ همان نوبت باقی می‌ماند و وارد معنای ثابت
اقدام نمی‌شود؛ وگرنه تغییر نسخه، بازیابی تجربهٔ اقدام قبلی را قطع می‌کرد.

در fixture فشار خواب: نخست «راه‌رفتن» درخواست شد و بدن «حفاظت» اجرا کرد؛ سپس
دو درخواست بعدی «مشاهده» بودند و همان اجرا شد. این رفتار بعد از راه‌اندازی سرد
هم آزموده شد. بهبود عمومیِ گفتگو، وزن‌های مدل یا یادگیری زیستی سنجیده نشده است.

## منابع و حدود

۷۰ فایل اصلی زیر `runtimes/tadash_body` بدون تغییر وارد شده‌اند. اثرانگشت‌ها پیش
از هر فرمان بررسی می‌شوند؛ اجرا روی یک کپی موقت و در فرایند جدا است تا نام‌های
ماژول قدیمی با برنامهٔ میزبان تداخل نکنند. فایل‌های defaults صرفاً در آن کپی
آزمایشی ساخته می‌شوند. checkpoint خصوصی قبلی و دفتر تعهدهای کتاب تغییر نمی‌کنند.

این مسیرِ محلی مستقل از نمونهٔ چهارابزاریِ `nasuraya_agent_loop` است. اتصال
چهار ابزار API آن نمونه به بدن، WorldModel مستقل و هستهٔ چهارمحوریِ ناسورایا
در این تغییر انجام نشده‌اند. احراز هویت تولیدکنندهٔ شاهد، مقابله با ویرایش مستقیم
پایگاه، اثر فیزیکی، اجرای چند بدن هم‌زمان و فرایند دائمی پس‌زمینه خارج از آزمون‌اند.

۱۱ آزمون تازهٔ اتصال و ۹۹ آزمون اصلیِ بستهٔ بازیابی‌شده گذشتند. گزارش و شواهد
در `evidence/` و `docs/nasuraya-body-loop-2026-10-13.md` قرار دارند.

## اصلاحات بازبینی مستقل

آزمون‌های اتصال اکنون ۱۶ موردند. شمار چرخهٔ کامل فقط اجرای برگشتیِ بدن با
رسید و checkpoint را می‌شمارد؛ شکست اجرا جدا گزارش می‌شود و فرمان `step` یا
`demo` در آن حالت کد خروج غیرصفر دارد. تلاش شکست‌خورده بودجه را مصرف می‌کند و
تکرار شناسهٔ آن، رسید شکست را بدون اجرای دوباره برمی‌گرداند. وتوی محافظ بدن
همچنان یک چرخهٔ موفق اجراست، حتی اگر با اقدام درخواستی تطابق نداشته باشد.

مدت باید بین ۰٫۱ و ۱ ثانیه و مضربی از ۰٫۱ باشد؛ شناسهٔ تصمیم حداکثر ۱۰۹
نویسه دارد تا پیشوند رویداد از سقف ۱۲۰ نویسهٔ بدن تجاوز نکند. ورودی نامعتبر
پیش از مصرف مشاهده یا بودجه رد می‌شود. قفل اکنون روی خود inode پایگاه است؛
hard link رد می‌شود چون فایل‌های WAL در SQLite به نام مسیر وابسته‌اند.
پایگاه با مجوز ۰۶۰۰ و پوشهٔ خروجی تازه با ۰۷۰۰ ساخته می‌شود. مجوز پایگاه موجود
فقط پس از تأیید نشانگر این حلقه محدود می‌شود؛ دفترِ غیرمرتبط دست‌نخورده می‌ماند.

## اتصال عامل API به بدن

فرمان صریح `api` از همان Agents API موجود در نمونهٔ عامل استفاده می‌کند.
میزبان `BodyAPIHost` سه ابزار محدود دارد: `observe_body`، `evaluate_body` و
در حالت bounded، `request_body_action`. ابزار سوم فقط ترجیح «walk» یا
«observe» را به گزینه‌های هستهٔ تصمیم می‌دهد؛ بازخورد می‌تواند ترجیح را عوض
کند و حفاظت بومی بدن می‌تواند اقدام را وتو کند. مدل به checkpoint کامل،
حافظهٔ خصوصی، ورودی دلخواه بدن، shell، فایل یا شبکه ابزار دسترسی ندارد.

خلاصهٔ ارسالی فقط شمارهٔ نسخه، هش checkpoint، ساعت شبیه‌سازی و هشت متغیر
کمینهٔ fixture تولیدشده است. نتیجهٔ فراخوانی با هویت session/turn/call در
همان SQLite ذخیره می‌شود. تغییر payload با هویت یکسان رد می‌شود؛ سقف
فراخوانی‌ها پس از restart ثابت می‌ماند. مشاهده به همان session و turn بسته
است. نتیجهٔ بدنی که commit شده ولی پاسخ ابزارش ثبت نشده از تصمیمِ کامل
بازیابی می‌شود؛ درخواستِ حل‌نشده دوباره اجرا نمی‌شود و اقدام تازه را مسدود
می‌کند. مسیر API اکنون شناسهٔ نشست و دور را جدا از هدف ذخیره می‌کند و پس از
قطع جریان، به همان نشست متصل می‌شود؛ جزئیات و حدود آن در
[گزارش بازیابی ایمن](../../docs/nasuraya-api-recovery-2026-10-13.md) آمده است.

آزمون‌های بدون سرویس زنده:

```sh
python3 -m examples.nasuraya_body_loop api-test
.ci-env/bin/python -m examples.nasuraya_body_loop api-test
```

آزمون دوم SDK نصب‌شده و transport کنترل‌شده را نیز بررسی می‌کند. این دو
فرمان کلید نمی‌خوانند و API زنده مصرف نمی‌کنند. فرمان `api` فقط در انتخاب
صریح کاربر کلید را از محیط یا `.env.local` خصوصیِ کنار مخزن می‌خواند؛ کلید
داخل payload، گزارش یا کنترل نسخه قرار نمی‌گیرد. فایل کلید باید 0600 باشد.

شروع فقط‌خواندنی در یک session تازه و خروجی تازه:

```sh
python3 -m examples.nasuraya_body_loop start --fixture sleep --mode observe --max-actions 0 --session /tmp/new-body-observe.sqlite
python3 -m examples.nasuraya_body_loop api --session /tmp/new-body-observe.sqlite --api-mode observe --model gpt-6-astra --target-cycles 0 --output-dir /tmp/new-body-observe-report
```

برای درخواست یک چرخه از fixture تازه با بودجهٔ محدود:

```sh
python3 -m examples.nasuraya_body_loop start --fixture normal --mode bounded --max-actions 3 --session /tmp/new-body-api.sqlite
python3 -m examples.nasuraya_body_loop api --session /tmp/new-body-api.sqlite --api-mode bounded --model gpt-6-astra --target-cycles 1 --output-dir /tmp/new-body-api-report
```

این فرمان‌ها به SDK اختیاری و صورتحساب فعال API نیاز دارند. در بررسی ۱۳ اکتبر،
جلسهٔ زنده ساخته شد ولی پیش از هر ابزار با خطای داخلی/پایان مهلت متوقف و حذف
شد؛ یک درخواست تشخیصی مستقل `billing_not_active` داد. پس اتصال کد و اجرای
بدن در آزمون کنترل‌شده تأیید شده‌اند؛ موفقیت مدل زنده هنوز تأیید نشده است.

## حفظ هدفِ دور عامل پس از توقف

هر دور عامل اکنون یک `--run-id` محلی دارد؛ مقدار پیش‌فرض `main` است. قرارداد
حالت، هدف تعداد چرخه‌ها و سقف فراخوانی‌ها در SQLite نگه داشته می‌شود. بازشدن
دوبارهٔ همان شناسه، ادامهٔ همان هدف است؛ مقدار هدف یا حالت آن خودکار عوض
نمی‌شود. برای کار تازه باید شناسهٔ تازه را صریح انتخاب کرد، مثلاً
`--run-id next-inspection`. هدف تازه بودجهٔ کلی بدن یا سقف API را صفر نمی‌کند.

پیشرفت دور فقط از تصمیم‌های مربوط به فراخوانی‌های خودش می‌آید؛ اجرای محلی
دیگر یا رسید تاریخیِ بدون شناسهٔ دور، به‌عنوان انجام این هدف شمرده نمی‌شود.
رسیدهای تاریخی همچنان بدون تکرار بدن قابل‌بازپخش‌اند. مشاهده به دور، session
و turn خودش بسته است. نتیجه و نشانه‌های مشاهده/ارزیابی در یک تراکنش ثبت
می‌شوند. حفظ هدف و بازیابی نشست API دو لایهٔ جدا هستند.

دیدن هدف و خودمدل کاهش‌یافته، بدون SDK یا کلید و بدون API زنده:

```sh
python3 -m examples.nasuraya_body_loop run-status --session /tmp/new-body-api.sqlite --run-id main
```

آزمون‌های ابزار API/بدن علاوه بر ۲۰ مورد قبلی، ۲۱ سناریوی بازیابی جدید دارند؛
شامل قطع جریان، رسید تکراری، نتیجهٔ نامعلوم، فرایند تازه و SDK با HTTP
شبیه‌سازی‌شده. هیچ‌یک اجرای مدل زنده نیستند.

پیش‌فرض فرمان `api`، `--api-recovery resume --max-reconnects 1` است؛ هدف و
سقف‌های قبلی باید با همان `--run-id` حفظ شوند. اجرای دوباره همان فرمان با
پوشهٔ خروجی تازه، نشست ذخیره‌شده را بررسی و دنبال می‌کند. پس از تأیید پایان
نشست قبلی و تطبیق رسیدها، `--api-recovery fresh` نشست تازه‌ای برای همان هدف
می‌سازد. این گزینه اجازهٔ جایگزینی نشست فعال یا تکرار اثر نامعلوم را نمی‌دهد.

## ادامهٔ یک مأموریت تکمیل‌شده

میزبان می‌تواند برای مأموریتی تازه، مجوز محدود ثبت کند و هم‌زمان بدن، هدف‌ها،
مصرف قبلی و بازخوردها را حفظ کند. تکرار همان مجوز بودجه را دوباره پر نمی‌کند.
بودجهٔ ابزار مأموریت تازه جداست و هدف‌های قدیمی نمی‌توانند آن را مصرف کنند.
[قرارداد و فرمان‌های ادامه](../../docs/nasuraya-explicit-continuation-v01.md).

## بازیابی و بازگشت به حرکت

ابزار `request_body_action` اکنون `sleep` و `rest` را نیز به همان DecisionCore،
ReflectionCycle و بدن بومی می‌رساند. سقف هر اقدام همچنان یک ثانیه است؛ بودجه‌ها،
مشاهدهٔ تازه، جلوگیری از تکرار و حق وتوی بدن حفظ می‌شوند. دستور مدل درخواست خواب
را برای فشار خواب بیش از ۰٫۶۵، استراحت را برای خستگی بیش از ۰٫۴۵ و سپس حرکت را
پیشنهاد می‌کند. پیشنهاد، تضمین انتخاب یا اجرای بدن نیست.

`recovery_step()` یک کنترل‌گر محلی و محدود است: مشاهدهٔ تازه، حداکثر یک درخواست
اقدام و ارزیابی. هیچ مدل زبانی، شبکه یا بودجهٔ تازه‌ای را خودکار فراخوانی نمی‌کند.
هدف بازگشت به یک چرخهٔ حرکت بومی به صورت قرارداد ذخیره می‌شود؛ پیشرفت از رسیدهای
واقعاً ثبت‌شده بازسازی می‌شود. تمام‌شدن بودجه یا هدف شمارشیِ دورها، به معنی
بازیابی کامل نیست. تاریخچهٔ وتو در وضعیت خواب‌آلود نگه داشته می‌شود؛ پس از خواب
یا استراحتِ ثبت‌شده و مشاهدهٔ آمادگی، حرکت در زمینهٔ شواهد `optional-motion/ready`
بررسی می‌شود تا وتوی وضعیت پیشین بی‌انتها به وضعیت تغییرکرده تعمیم نیابد.

دو اجرای محلیِ قابل بازتولید، از ریشهٔ مخزن و با Linux/Python 3.11+:

```bash
PYTHONPATH="$PWD/runtimes/tadash_body:$PWD" python -m examples.nasuraya_body_loop.recovery_demo --output-dir /tmp/nasuraya-recovery-ready
PYTHONPATH="$PWD/runtimes/tadash_body:$PWD" python -m examples.nasuraya_body_loop.recovery_demo --source-session /path/to/completed/session.sqlite --output-dir /tmp/nasuraya-recovery-continuation
```

اجرای نخست، یک fixture تازه و صریحاً نزدیک آستانهٔ خواب می‌سازد: یک خواب، سپس
توقف فرایند، بازیابی هدف در فرایندی تازه و یک چرخهٔ حرکت بومی. این fixture شاهدِ
درمان وضعیت ذخیره‌شدهٔ کاربر نیست. اجرای دوم، از SQLite موجود پشتیبان خصوصی
می‌گیرد و با یک مجوز میزبان برای سه اقدام و دوازده فراخوانی ابزار ادامه می‌دهد؛
تمام هدف‌های پیشین باید کامل و بودجهٔ قبلی تمام شده باشد. فایل مبدأ، تنظیم اولیه،
تصمیم‌ها و قرارداد هدف‌های قبلی حفظ می‌شوند. بازخوانی نهایی صفر اقدام اجرا می‌کند.

آزمون‌ها از فرمان `python -m examples.nasuraya_body_loop api-test` اجرا می‌شوند.
`--preferred-action sleep` یا `rest` برای فرمان‌های محلی `step` و `demo` نیز
در دسترس است. فرمان‌ها با همان بودجه و محدودیت‌های قبلی اجرا می‌شوند.

معادلات و manifest هفتاد فایل بدن بومی تغییر نکرده‌اند. افت فشار خواب، اثر یک
معادلهٔ شبیه‌ساز است؛ رفع کامل خستگی عضلانی یا افزایش توان عمومی از آن نتیجه
گرفته نمی‌شود. خواب، استراحت، مشاهده و بازگشت به حرکت جداگانه در رسیدها ثبت
می‌شوند؛ عبور زمان و بازکردن پایگاه، خوابِ انجام‌شده محسوب نمی‌شوند.
