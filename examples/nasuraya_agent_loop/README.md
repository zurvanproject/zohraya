# نمونهٔ مستقل حلقهٔ عامل ناسورایا / تداش

**افزونهٔ ۲۰ اکتبر ۲۰۲۶:** اتصال جداگانهٔ [کارگاه عاطفی](../nasuraya_affect/README.md#execute-the-bounded-synthetic-workshop)
از `ToolHost` همین پوشه استفاده می‌کند و هستهٔ تصمیم، حافظهٔ عاطفی و بازخورد
ابزار را به هم وصل کرده است. شرح زیر دربارهٔ backendهای قدیمی این نمونه است؛
دامنه و شواهد اتصال تازه در [گزارش آن](../../docs/nasuraya-affective-workshop-v01-fa.md) آمده‌اند.

این نمونه حلقهٔ مشاهده ← انتخاب کنش ← اجرای ابزار ← ارزیابی نتیجه را واقعاً
در یک کارگاه ساختگی اجرا می‌کند. `FixturePolicy` فقط سیاست ثابت آزمون است؛
هستهٔ تصمیم‌گیری ناسورایا نیست. انرژی و گرمای این مثال دادهٔ ساختگی‌اند و از
بدن محاسباتی تداش خوانده نمی‌شوند.

تمام فایل‌های تغییر فقط زیر `examples/nasuraya_agent_loop/` هستند. کدهای
`core_mechanics.py`، مدل خود، Decision Core و شبیه‌ساز بدن وارد یا تغییر نمی‌شوند.
هیچ وابستگی به PyTorch یا کلید API برای اجرای اصلی وجود ندارد.

## اجرا از ریشهٔ مخزن

Python 3.10 یا بالاتر کافی است:

```bash
python -m unittest discover -s examples/nasuraya_agent_loop/tests -v
python -m examples.nasuraya_agent_loop --output-dir /tmp/nasuraya-demo-01
```

پوشهٔ خروجی باید تازه باشد. فرمان سه فایل می‌سازد:

| فایل | محتوای قابل‌بازبینی |
| --- | --- |
| `events.jsonl` | مشاهده، انتخاب، فراخوانی معتبر ابزار، وضعیت قبل/بعد، ارزیابی و توقف |
| `summary.json` | نتیجهٔ اندازه‌گیری‌شده، شمار کنش و رویداد، وضعیت نهایی |
| `report.md` | خلاصهٔ اجرا و نمایهٔ رویدادها |

کد خروج صفر فقط برای `completed` است. توقف در سقف، رد ابزار یا خطا کد ۱ می‌دهد.
تکرار فرمان با همان پوشه مجاز نیست و خروجی قبلی بازنویسی نمی‌شود.
رشته‌های توضیح کنش کوتاه‌اند؛ زنجیرهٔ استدلال خصوصی ذخیره نمی‌شود.

## سناریو و ابزارها

وضعیت آغازین: انرژی ۴۵، گرما ۵۰، سه کار باقی‌مانده، صفر کار انجام‌شده.
ارقام واحد زیستی یا پزشکی ندارند. قاعدهٔ انتخاب آزمون:
اگر انرژی کمتر از ۳۵ یا گرما بیشتر از ۶۵ باشد، یک گام استراحت؛ وگرنه یک کار.

| ابزار | ورودی | اثر واقعی روی شبیه‌سازی |
| --- | --- | --- |
| `observe_state` | `{}` | دریافت کپی وضعیت؛ اجازهٔ یک کنش بعدی |
| `recover` | `ticks` عدد صحیح ۱ تا ۳ | در هر گام انرژی +۲۰، گرما −۲۰، با محدودیت ۰ تا ۱۰۰ |
| `process_job` | `{}` | یک کار؛ انرژی −۲۰، گرما +۲۰ |
| `evaluate_state` | `{}` | محاسبهٔ مستقل موفقیت و ایمنی از وضعیت میزبان |

موفقیت: صف خالی، انرژی دست‌کم ۱۵ و گرما حداکثر ۸۵.
ابزارهای تغییردهنده بدون مشاهدهٔ تازه، در حالت مشاهده، پس از موفقیت یا پس از
مصرف بودجه رد می‌شوند. نام ناشناخته، کلید اضافی، عدد بولی یا خارج از محدوده
نیز رد می‌شود. عامل هیچ ابزار shell، شبکه، مسیر فایل یا دسترسی به مخزن ندارد.
نوشتن گزارش فقط توسط میزبان انجام می‌شود.

خودمختاری در این مثال با `--mode observe|bounded` و `--max-actions` تنظیم می‌شود.
`observe` وضعیت را می‌خواند و کنش تغییردهنده را رد می‌کند؛ هیچ تأیید دستی خودکار
یا دامنهٔ دسترسی نامحدود وجود ندارد. سقف گام اجرای محلی `--max-steps` است.

```bash
python -m examples.nasuraya_agent_loop --mode observe --output-dir /tmp/nasuraya-observe-01
python -m examples.nasuraya_agent_loop --max-actions 2 --output-dir /tmp/nasuraya-budget-01
```

## اتصال اختیاری و جدا به Agents API

مستندات رسمی بررسی‌شده در ۱۳ اکتبر ۲۰۲۶:

- [معرفی Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview/)
- [مقایسهٔ Agents API، Agents SDK و Responses API](https://developers.openai.com/api/docs/guides/agents)
- [تعریف تابع و بازگرداندن نتیجه](https://developers.openai.com/api/docs/guides/agents-api/tools/functions)
- [رویدادها و پایان واقعی نوبت](https://developers.openai.com/api/docs/guides/agents-api/sessions/events)
- [پیکربندی محیط بدون sandbox](https://developers.openai.com/api/docs/guides/agents-api/configuration)
- [نصب SDK و مجوز کلید](https://developers.openai.com/api/docs/guides/agents-api/quickstart)

Agents API حلقه و جلسه را در سرویس مدیریت می‌کند؛ Agents SDK اجراکننده‌ای در برنامهٔ
توسعه‌دهنده است؛ این دو نام مترادف نیستند. اتصال این مثال واقعاً برای `beta.agents`
نوشته شده و از SDK عامل‌ها یا Responses به‌عنوان جایگزین پنهان استفاده نمی‌کند.

در یک محیط مجزای Python، وابستگی‌های اختیاری را نصب کنید. نسخهٔ `openai==3.29.0`
در این محیط نصب و با مسیر کامل ارسال درخواست و خواندن SSE روی پاسخ‌های ساختگی
آزموده شد. وابستگی `socksio` نیز برای پراکسی SOCKS این محیط لازم بود و نصب شد.
این آزمون‌ها هیچ درخواست شبکه یا استنتاج مدل ندارند؛ دسترسی حساب هنوز آزموده نشده.

```bash
python -m venv /tmp/nasuraya-api-env
/tmp/nasuraya-api-env/bin/python -m pip install -r examples/nasuraya_agent_loop/requirements-api.txt
/tmp/nasuraya-api-env/bin/python -m examples.nasuraya_agent_loop --check-api
# OPENAI_API_KEY را در محیط اجرا از محل امن خود تنظیم کنید.
# YOUR_AVAILABLE_MODEL را با مدل مجاز حساب خود جایگزین کنید.
/tmp/nasuraya-api-env/bin/python -m examples.nasuraya_agent_loop \
  --backend agents-api --model YOUR_AVAILABLE_MODEL \
  --max-actions 12 --max-calls 40 --timeout-seconds 60 \
  --output-dir /tmp/nasuraya-api-run-01
```

`--check-api` نسخه و قابلیت SDK و موجودبودن کلید را بدون درخواست API بررسی می‌کند.
کد خروج ۲ یعنی پیش‌نیاز ناقص؛ متن خروجی دلیل دقیق را نشان می‌دهد و مقدار کلید را
نمایش نمی‌دهد. برای ورود کلید از ترمینال تعاملی می‌توان به فرمان اجرای زنده
`--prompt-api-key` افزود؛ ورودی مخفی فقط به همان client داده می‌شود و در فایل یا
متغیر محیطی ذخیره نمی‌شود. در ورودی غیرتعاملی این گزینه ورود آشکار کلید را رد می‌کند.

آزمون‌های پایه بدون SDK اجرا می‌شوند؛ ده آزمون SDK و HTTP محلی در آن محیط skip
می‌شوند. پس از نصب وابستگی‌های اختیاری، همان فرمان unittest هر ۵۸ آزمون را اجرا می‌کند.

طبق quickstart، کلید به `api.agents.read`، `api.agents.write` و
`api.responses.write` نیاز دارد. SDK هدر `OpenAI-Beta: agents=v1` را می‌افزاید.
کلید فقط از محیط میزبان خوانده می‌شود و در ابزار، گزارش یا مخزن قرار نمی‌گیرد.
اجرای زنده مشمول هزینه، دسترسی حساب و محدودیت‌های ایمنی API است.

روال اتصال:

1. ساخت جلسه با `environment={"type":"none"}`، فقط چهار ابزار تابعی و ورودی اولیهٔ اجباری.
2. دریافت stream در همان درخواست ساخت (`stream=True`)؛ ثبت شناسهٔ جلسه از رویداد ساخت، پیش از اجرای ابزارها.
3. اجرای فراخوانی فقط از `session.required_actions` در رویداد
   `agent.session.requires_action`؛ آیتم تاریخی به‌تنهایی اجرا نمی‌شود.
4. بازگرداندن `agent.session.input.tool_result` با `turn_id` و `call_id` اصلی.
5. ارزیابی نتیجهٔ هر کنش توسط میزبان و بررسی موفقیت واقعی در پایان نوبت اصلی.
6. بستن stream و تلاش برای حذف جلسه، حتی هنگام خطا یا توقف.

بودجهٔ فراخوانی‌های یکتا، کنش‌ها، ۵۰۰ رویداد و زمان محدود است. بسته‌شدن stream،
idle شدن جلسه یا ادعای موفقیت مدل معیار موفقیت نیست. خطا، لغو، ناتمام‌ماندن جریان
و تکمیل نوبت با هدف برآورده‌نشده وضعیت‌های جدا دارند.
تایمر جریان محلی را می‌بندد؛ درخواست‌های عادی SDK timeout ده‌ثانیه‌ای و صفر retry دارند؛ درخواست stream ساخت
جلسه، timeout متناسب با سقف کل اجرای آزمون دارد.
حذف جلسه best effort است؛ پاسخ ۴۰۹ باعث درخواست لغو و حداکثر سه تلاش محدود برای حذف می‌شود: قطع شبکه می‌تواند مانع توقف یا حذف فوری سمت سرویس شود؛
در آن حالت `api_cleanup_failed` و شناسهٔ جلسه برای پیگیری ثبت می‌شوند.
خلاصه نیز `cleanup_status` را مستقل از موفقیت هدف نمایش می‌دهد. شناسهٔ نوبت
در فراخوانی و رویداد پایانی باید با نوبت اصلی تطابق داشته باشد؛ موفقیت یک نوبت
نامرتبط پذیرفته نمی‌شود. ساخت زیرعامل در پیکربندی جلسه غیرفعال شده است.

## اجرای هدایت‌شده در همین گفتگو

`guided.py` انتخاب خودکار ندارد؛ فراخواننده وضعیت را می‌خواند و کنش را مشخص می‌کند.
در اجرای ثبت‌شدهٔ این گفتگو، خود دستیار فراخواننده بود: انرژی ۲۹، گرما ۷۸ و سه
کار؛ انتخاب بازیابی سه‌گامی و سپس سه پردازش، هدف را با چهار کنش محقق کرد.
۴۲ رویداد، وضعیت نهایی و checkpoint زیر `evidence/chat_guided/` قرار دارند.
در این اجرا هیچ فراخوانی مستقل OpenAI API انجام نشد.

checkpoint پس از هر فرمان با جایگزینی اتمی ذخیره می‌شود. وضعیت، شمار کنش، توالی
رویداد و مشاهدهٔ تازه هنگام بارگذاری کنترل می‌شوند؛ توقف و شروع فرایند، بودجه را
صفر نمی‌کند. این بازیابی فقط برای همین دنیای ساختگی است و بازیابی اثر ابزارهای
بیرونی یا جلسهٔ API را پیاده‌سازی نمی‌کند. checkpoint ضد‌دستکاری نیست.

```bash
python -m examples.nasuraya_agent_loop.guided start --session /tmp/guided-01.json --energy 29 --heat 78 --jobs 3
python -m examples.nasuraya_agent_loop.guided observe --session /tmp/guided-01.json
python -m examples.nasuraya_agent_loop.guided act --session /tmp/guided-01.json --tool recover --ticks 3 --reason 'prepare for work'
```

`loopback.py` یک سرویس آزمایشی با انتخاب ثابت و HTTP/SSE واقعی، فقط روی
`127.0.0.1` فراهم می‌کند و پس از آزمایش خاموش می‌شود. شش سناریو شامل موفقیت،
رویداد تکراری، قطع جریان، ابزار نامعتبر، خطای حذف و نوبت نامرتبط آزموده شدند.
این سرویس مدل زبانی نیست؛ شواهد آن در `evidence/loopback_http/` قرار دارند.

سنجش شبکهٔ وضعیت‌های ساختگی، ۴۸۴ ترکیب انرژی/گرما/تعداد کار را با سیاست ثابت
آزمون ارزیابی کرد؛ همه به هدف رسیدند. این شمار، سنجش FixturePolicy است و عملکرد
مدل زبانی یا بهبود ناسورایا را اندازه نمی‌گیرد. فرمان تکرار:

```bash
python -m examples.nasuraya_agent_loop.evaluate_grid --output /tmp/nasuraya-grid-01.json
```

فراخوانی تکراری با همان شناسه در همان فرایند دوباره اثر نمی‌گذارد؛ نتیجهٔ ذخیره‌شده
دوباره ارسال می‌شود. تغییر payload با همان شناسه رد می‌شود. **بازیابی پس از crash یا
اجرای مجدد فرایند پیاده‌سازی نشده**؛ استفادهٔ تولیدی به ذخیرهٔ تراکنشی بادوام و بررسی
اثر اجرا پیش از تکرار نیاز دارد. لاگ فعلی ضد‌دستکاری یا سامانهٔ یادگیری پایدار نیست.

## نتیجهٔ آزمون زندهٔ ۱۳ اکتبر ۲۰۲۶

دو جلسهٔ واقعی Agents API ساخته شدند. اجرای اول با timeout خواندن متوقف شد و
جلسهٔ آن در پیگیری حذف شد. اجرای دوم پیش از اولین کنش خطای `internal_error` داد

اجرای موفق حلقه نیست؛ هیچ کنش ساختگی از مدل زنده اجرا نشده است.

کلید در فایل محلیِ تأییدشده خارج از فایل‌های منبع قرار دارد؛ هیچ مقدار کلید در
این مخزن ثبت نشده است. پیش از آزمون بعدی باید صورتحساب API حساب فعال شود.
